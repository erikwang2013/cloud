## 3. Problemas bloqueantes (en orden de dependencia)

### B1. El formato de ENCRYPTION_MASTER_KEY no coincide con lo que exige el código → el worker de admin se cae al arrancar
- **Síntoma**: tras `php start.php start`, los 4 workers salen todos con excepción (el puerto queda colgado pero las peticiones nunca se responden; las conexiones se acumulan en el accept backlog); log:
  `InvalidArgumentException: Master key must be exactly 32 bytes. in vendor/erikwang2013/encryption/src/EncryptionManagerFactory.php:29`
- **Causa raíz**: `ENCRYPTION_MASTER_KEY=y1Odnbg50NHEvvLHGb8aexKqy8AQ7izm0x+yoEgrYCU=` en `admin/.env` es **base64 de 44 bytes**; `EncryptionManagerFactory::fromMasterKey()` exige **32 bytes en bruto** (el comentario de `admin/config/encryption.php:30` también dice "64 hex characters"). Pero `.env.example:64` lo marca como base64 — la configuración contradice la convención del código.
- **Complemento**: `support/bootstrap.php:47` usa `Dotenv::createUnsafeMutable()->load()`; **la sobrescritura de env a nivel de proceso queda cubierta por los valores de .env**, no se puede eludir con parámetros de arranque (comprobado dos veces, ambas fallan).
- El resultado de decodificar en base64 esa key da exactamente 32 bytes (hex `cb539d9d…6025`), es decir, el formato correcto es el valor decodificado en base64.

### B2. Falta `config/database.php` → la capa de base de datos no existe
- **Síntoma**: `/account/login` → 500 `BusinessException: 请重启webman` (`app/controller/AccountController.php:263` en `checkDatabaseAvailable()`, que lanza si `!config('database')`).
- **Causa raíz**: ese archivo lo genera el asistente de instalación y está en gitignore; nunca existió en el repositorio (`git ls-files` sin registros). Falta también `config/thinkorm.php`.

### B3. Falta `install.sql` → el asistente de instalación no se puede ejecutar
- **Síntoma**: el `step1` del asistente (`InstallController.php:105`) comprueba `base_path().'/install.sql'`; si falta, devuelve "数据库SQL文件不存在" (el archivo SQL de base de datos no existe). El archivo no existe en el repositorio.
- Impacto: la única vía oficial para arreglar B2 (asistente UI) tampoco funciona.

### B4. Todas las rutas de recursos estáticos de las vistas usan el prefijo `/app/admin/`, y ese prefijo no tiene ningún mapeo → toda la UI sin estilos, JS 404
- **Síntoma** (medido en página de login/página de instalación/marco principal): `/app/admin/component/pear/css/pear.css`, `/app/admin/admin/css/reset.css`, `/app/admin/component/layui/layui.js` etc. todos 404; `ReferenceError: layui is not defined`; los formularios no se pueden enviar.
- **Causa raíz**: los estáticos están realmente en `public/admin/`, `public/component/` (webman los sirve como `/admin/...`, medido 200); mientras que `app/view/account/login.html`, `app/view/index/install.html`, `app/view/index/index.html` etc. referencian todos `/app/admin/...`. `config/route.php` solo tiene 4 rutas explícitas `/app/admin/` (captcha/dict/dashboard-data/table-export), `config/static.php` no tiene mapeo de prefijo, y `docker/nginx.conf` y `docker/nginx-admin.conf` tampoco tienen `location /app/admin`. La convención de URLs entre frontend y backend es inconsistentemente global (el POST de formulario `/app/admin/account/login` → 404; el endpoint real debería estar en la raíz `/account/login`).

### B5. El destino de redirección sin login es erróneo → las páginas de negocio acaban todas en la página 404 de Chrome
- **Síntoma** (medido en /user/index, /order/index, /product/index, /supplier/index, /config/index, /role/index, /admin/index, /ticket/index, /index/dashboard, /dashboard/index): devuelven 200, pero la página se redirige por JS a `http://127.0.0.1:8788/app/admin` → esa URL da 404 → Chrome renderiza "página no encontrada".
- **Causa raíz**: sin login, `app/middleware/AccessControl.php:45` devuelve `admin_error_401_script()` (`app/functions.php:93`), cuyo contenido es `<script>top.location.href = '/app/admin';</script>` — la dirección de la página de login está escrita a fuego como `/app/admin`, el mismo error de convención de rutas que B4.
- Adicional: `/payment_channel/index`, `/coupon/index`, `/domain_tld/index`, `/dns_zone/index`, `/invoice/index`, `/report/index` dan directamente `ERR_HTTP_RESPONSE_CODE_FAILURE` (fallan ya en la capa de controlador/ruta, sin llegar a la redirección).

### B6. La ruta raíz da 500: faltan los datos de `system_config`
- **Síntoma**: tras completar manualmente la configuración de B2, `GET /` (punto de entrada del render de la página de login, `IndexController::index`) → 500 `ErrorException: json_decode(): Passing null to parameter #1 … in app/controller/IndexController.php:49`.
- **Causa raíz**: `Option::where('name','system_config')->value('value')` devuelve null (no existe esa fila en la BD — esta BD no la generó el asistente de instalación); `json_decode(null)` en PHP 8.3 dispara el deprecation y lanza error. Es decir, la página de login se cae directamente cuando los datos no se inicializaron vía asistente.

## 5. Resumen de defectos UI encontrados

### Primera ronda (entorno en su estado original, bloqueantes)

1. **B1 (bloqueante)** la clave maestra del `.env` es base64 y no cumple los 32 bytes que exige el código → el servicio no arranca en absoluto. Reproducción: `cd admin && php start.php start -d`.
2. **B2/B3 (bloqueantes)** faltan los artefactos de instalación (config/database.php, install.sql) y además el asistente no se puede ejecutar → la aplicación no se puede inicializar.
3. **B4 (bloqueante)** las rutas de recursos de vistas de todo el sitio `/app/admin/...` no coinciden con la ubicación real de los estáticos ni con los prefijos de ruta → sin estilos, sin JS, formularios inutilizables.
4. **B5 (bloqueante)** la redirección 401 sin login está escrita a fuego como `/app/admin` → todas las páginas de negocio saltan a un enlace muerto.
5. **B6** el render de la página de login no tiene fallback cuando falta la fila `system_config`; `json_decode(null)` da 500 directo (en PHP 8.3 el deprecation se eleva a excepción).

### Segunda ronda (medida tras login, problemas sistémicos)

6. **W1. El WAF bloquea URLs de negocio**: `admin/app/middleware/WafMiddleware.php:75` escanea la ruta de la URL con regex SQLi/XSS (`config/security.php`: `\b(union|select|insert|update|delete|drop|...)\b`, `\balert\b` etc.):
   - `/alert/index` acierta la regla XSS por contener "alert" en la URL → **403**;
   - todos los endpoints de datos CRUD (`/user/select`, `/user/insert`, `/user/update`, `/user/delete`, `/order/select`…) aciertan reglas SQLi como `\bselect\b` → **403**.
   - Impacto: **la carga de datos de todas las listas y las altas/bajas/modificaciones son completamente inutilizables en el navegador** (las peticiones `SELECT_API` del frontend dan todas 403).
7. **W2. La convención de guion bajo en URLs no se cumple + enlaces de menú todos muertos**: el enrutado automático de webman no soporta guion bajo en nombres de controlador — `/order_item/index` da 404, `/orderitem/index` da 200 (los 47 páginas solo se alcanzan concatenando la URL en camelCase). Pero todos los href de `config/menu.php` y `config/business_menu.php` son `/app/admin/<snake_case>/index` (p. ej. `/app/admin/payment_channel/index`) → **cada elemento de la navegación lateral es un enlace muerto (404 o 403)**.
8. **W3. La constante JS SELECT_API de los datos de tablas no está definida**: el JS de las páginas (404 en `/app/admin/...`, resto de B4) referencia constantes como `SELECT_API`/`INSERT_API` que no se inyectan → las tablas de las listas renderizan sin datos, sin paginación/búsqueda.
9. **W4. 11-15 errores de consola de 404 de recursos estáticos por página**: el impacto continuo de B4 — las 47 páginas 200 están todas sin estilos, con `layui is not defined`, y los formularios y popups no funcionan.

**Resumen**: el esqueleto de las páginas se renderiza (47/51), pero la navegación lateral (W2), la carga de datos de tablas (W3+W1) y todas las operaciones de escritura CRUD (W1) no funcionan en el navegador — en la práctica el panel no se puede operar.

## 6. Páginas no probadas y motivos

- **Operaciones de escritura CRUD (envíos de formularios de alta/edición/borrado)**: los endpoints de datos están todos bloqueados por el WAF (W1) + el JS de los formularios no funciona (B4/W3); no se puede completar ninguna escritura vía UI. Si se corrigen W1 y B4, se puede complementar la prueba con los endpoints insert/update/delete.
- **Páginas tras login**: ya medidas todas en la segunda ronda (47/51 render correcto, ver §4.2); lo no cubierto es solo la navegación de menús (enlaces muertos W2) y la carga de datos de tablas (W1/W3).
- **apps/ (clientes Flutter/HarmonyOS)**: requieren dispositivo real/emulador; fuera de alcance en esta ronda (el encargo se centra en Web).
- **Páginas de API de negocio de service**: sin UI Web (8787 `/` y `/install.php` ambos 404, API pura); las pruebas a nivel de interfaz las cubre la tarea #13.

- Nota: si `.env` está en git (este repositorio tiene registros de su commit) debería añadirse a .gitignore; la clave maestra conviene inyectarla por env y no en claro en el repositorio.
