## Defectos de aplicación (código actual, reproducidos)

### Defecto 1: longitud incorrecta de la clave de cifrado de campos de base de datos encryptable → 500 en todas las escrituras de campos cifrados
- Síntoma: `POST /api/auth/register`, `POST /api/auth/login` (con contraseña correcta), `POST /api/auth/refresh`, `POST /api/user/addresses` devuelven todos HTTP 500 `Server internal error` (register, envuelto por el canal cifrado, devuelve 200 + payload; al descifrar, también `Server internal error`).
- Causa raíz: en `.env`, `ENCRYPTION_CIPHER=aes-128-ecb` (requiere clave de 16 bytes) + `ENCRYPTION_KEY=YKBEUxiX/G8HwVS4S+/UxQ==` (16 bytes codificados en base64, pero el código no aplica base64_decode antes de usarla; la longitud real es de 24 caracteres) → `vendor/erikwang2013/encryptable/src/Encrypter.php:74` lanza `MissingEncryptionKeyException: The encryption key must be 16 bytes for cipher [aes-128-ecb]`.
- Superficie de impacto: toda escritura en modelos con cast `Encryptable`: users (email/phone/password_hash), refresh_tokens (token_hash/device_fingerprint), user_addresses (phone/address), user_kyc, payment_channels, suppliers, host_machines, provider_api. Es decir: registro, emisión de token al iniciar sesión, renovación de token y alta de direcciones quedan completamente inutilizables.
- Sugerencia de corrección: aplicar `base64_decode` a `ENCRYPTION_KEY` en `config/encryptable.php` (o poner la clave en claro de 16 bytes directamente en .env).
- Tratamiento en la prueba: tras el login, el token lo emite directamente el script de prueba llamando a `JwtAuth::issueAccessToken` (misma clave) para desbloquear el resto de la cadena; register/login/refresh/creación de dirección se verifican como sondas de defecto (PASS significa defecto confirmado; tras la corrección, la aserción pasará a FAIL para señalar la regresión).

### Defecto 2: los modelos admin mapean tablas `erik_*` (ausentes en las migraciones del repositorio) → CRUD totalmente caído si la tabla falta / datos desconectados de service si la tabla existe
- Síntoma: `admin/app/model/*.php` declaran todos `protected $table = 'erik_*'`. Durante la prueba se observaron dos formas:
  1. Tablas erik_* inexistentes (estado actual de la BD; las tablas erik_* fueron retiradas por el cambio concurrente de entorno): 9/12 endpoints de datos `/select` de admin devuelven `code=42 SQLSTATE[42S02] ... Table 'cloud_platform.erik_orders/erik_products/...' doesn't exist`; `/insert` también devuelve 42. Solo son utilizables user/role/audit_log, que mapean tablas reales (user→users, role→wa_roles).
  2. Tablas erik_* creadas manualmente (existieron brevemente tras crearlas otro agente a mitad de la prueba): `/select`, `/insert`, `/delete` de admin funcionan todos con code=0, pero las escrituras caen en `erik_products`, mientras que service solo lee `products` → el producto creado en admin no aparece en el listado de la tienda (la aserción sonda confirmed listed=n; tras la corrección pasará a FAIL para señalar la regresión).
- Nota (anomalía observada): al ejecutar el E2E completo, el id(hashid) devuelto por `POST /app/admin/product/insert` no coincide con el id real de la fila insertada (p. ej. respuesta nE6vQwlYejMd→350964708271980544 vs fila real 350963879578173440); al usar el id de la respuesta para delete devuelve code=0 pero no coincide ninguna fila, borrado vacío silencioso (reproducido en dos ejecuciones completas); la sonda aislada (insert inmediatamente tras login) no lo reprodujo; parece relacionado con la temporización de peticiones o la generación del ID de nieve, no investigado a fondo. El script de prueba ahora consulta el id real de la fila por slug para borrar/limpiar.
- Superficie de impacto: la cadena de datos entre el panel admin y el escaparate queda rota (los datos gestionados en admin no se ven en la tienda, y viceversa); un id de respuesta de insert no fiable provoca que borrados/actualizaciones del cliente fallen en silencio.
- Sugerencia de corrección: en los modelos de admin, quitar el prefijo `erik_` de `$table` para apuntar uniformemente a las tablas reales de service (y completar migraciones/semillas); investigar la cadena de generación del id de respuesta del insert.
- Tratamiento en la prueba: los listados se verifican como sondas de defecto (code=0 o SQL 1146, ambos PASS = defecto confirmado; tras la corrección pasarán a FAIL para señalar la regresión); el borrado/limpieza usa el id real de la fila.

### Defecto 3: webman-scout (cliente de elasticsearch no instalado) → 500 en escrituras de User/Order/Ticket
- Síntoma: `PUT /api/user/profile` (incluida la restauración), `POST /api/orders`, `POST /api/tickets` devuelven todos HTTP 500 `Server internal error` (en el log: `ScoutException: Please install the ElasticSearch client`).
- Causa raíz: los modelos User/Product/Ticket/Order llevan el trait `Scout\Searchable` (config/plugin/webman-scout, driver por defecto = elasticsearch), pero el cliente `elasticsearch/elasticsearch` no está instalado → al guardar el modelo, la sincronización del índice lanza una excepción.
- Superficie de impacto: editar perfil, crear pedidos y enviar tickets quedan inutilizables (el carrito/agregar al carrito no se ve afectado).
- Sugerencia de corrección: instalar el cliente de elasticsearch y configurar un servicio ES disponible, o cambiar el driver a `database`/`null` (cuando la búsqueda no esté habilitada).
- Tratamiento en la prueba: verificación como sondas de defecto (PASS = defecto confirmado; tras la corrección pasará a FAIL para señalar la regresión).

## Hallazgo importante: el plugin de seguridad bloquea las pruebas locales
- El plugin security del código actual (erikwang2013/security-php) activa la detección `dns_rebinding`: cuando el Host es 127.0.0.1/localhost/IP de red interna, bloquea directamente con 403; tras 5 intentos consecutivos, la ip_blacklist banea 127.0.0.1 durante 15 minutos (almacenado en /tmp/security_storage.json, compartido por service/admin).
- Impacto: para probar la API desde esta máquina hay que enviar el Host con un nombre de host externo (esta prueba usa `Host: api.test.local` / `Host: admin.test.local`), si no, todo devuelve 403.
- Este comportamiento es el estado actual del código (configuración añadida tras el commit de las 18:37); el proceso antiguo iniciado a las 14:08 no tenía esta configuración, por eso los informes anteriores no muestran este bloqueo.

## Cómo ejecutar
```bash
# Requisitos previos: service 8787 + admin 8788 en ejecución; MySQL/Redis disponibles
php tests/api/run_api_e2e.php
```
- Idempotencia: el script se puede repetir (cada ejecución crea una cuenta de prueba nueva (inserción directa por SQL) y datos semilla nuevos, y limpia al terminar).
- Nota: si una prueba anterior disparó el baneo de seguridad (/tmp/security_storage.json contiene el ban de 127.0.0.1), hay que borrar ese archivo o esperar 15 minutos.
