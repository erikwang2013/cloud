## P4.1 Отдельный API-шлюз + единое ограничение частоты

### Текущее состояние (подтверждено чтением кода)

| Уровень | Текущее состояние |
|----|------|
| Пограничный шлюз | docker/nginx.conf выполняет роль L7-шлюза service: `limit_req_zone api 10r/s` (глобальное ограничение), proxy_pass 8787 (service), 8282 (ws). **admin — отдельный контейнер** (Dockerfile admin target, nginx-admin.conf listen 8788 proxy 8788), **без limit_req** |
| Ограничение на уровне приложения | `service/common/security/RateLimitMiddleware.php` уже существует: Redis INCR+expire, фиксированное окно, **только per-IP**, выбор правила по `ROUTE_MAP`, прикреплён к **явным маршрутам** (в route.php всего ~12 мест) |
| Конфигурация правил | `config/security.php rate_limits`: default/login/register/password_reset/oauth/captcha/sms/pay/upload/supplier_api/graphql, все содержат rate/burst/per, но **поле burst в настоящее время не используется** |
| Глобальные промежуточные слои | Ключ `''` в `config/middleware.php` уже поддерживает действие на все маршруты (10 пунктов: WAF/GeoBlock/Security и др.) |
| Пробелы | У `/graphql` (public + authenticated — два маршрута) **нет никакого ограничения частоты**; per-token ограничения нет; в ответе 429 нет заголовка `Retry-After`; у webhook нет исключений/отдельных правил |

### Решения

**D1: не создавать новый отдельный процесс шлюза.** nginx и есть шлюз (сетевой край + ограничение частоты + разделение маршрутов), единое ограничение частоты — внутри webman.
- Причина: отдельный gateway-контейнер потребовал бы новых зависимостей/новой топологии развёртывания/двойной аутентификации; при текущем масштабе одного инстанса это перепроектирование;
- Компромисс: на уровне шлюза невозможно дифференцированное ограничение по token/по маршруту (у nginx только per-IP зоны). Дифференциацию добирает приложение, на уровне nginx остаётся только грубая IP-подстраховка (существующие 10r/s повысить до 100r/s, чтобы не бить по бизнесу; при k6-проверке вернуть демонстрационный порог).
- Путь развития: при будущих нескольких инстансах/сервисах глобальный ограничитель из `config/middleware.php` переносится как есть в отдельный gateway-сервис — промежуточный слой не чувствителен к форме развёртывания.

**D2: единое ограничение = глобальный промежуточный слой + двухмерные вёдра (per-IP + per-token).**
- Убрать `RateLimitMiddleware` из явных маршрутов (в route.php фактически ~12 мест, ориентироваться на grep), повесить в глобальный список `''` в `config/middleware.php` (после WAF, перед бизнес-промежуточными слоями) — **естественно покрывает все маршруты приложения (включая два `/graphql`)**.
- **Семантика вёдер (явно, против обхода)**: `ratelimit:ip:{realIp}:{rule}` и `ratelimit:tok:{sha256(token)}:{rule}` — два вёдра считаются независимо, **превышение любого ведра даёт 429 (OR)**. Запрещено реализовывать по AND — при AND смена IP обходит per-IP ведро, смена token обходит per-token ведро.
- **Список исключений**: `/health*` (мониторинговые пробы) и `/api/payments/webhook/stripe` (проверка подписи — реальная линия обороны + Stripe 429 с автоотступом при повторе + по-прежнему действует грубая подстраховка nginx 100r/s; у ограничения здесь нет выигрыша в безопасности, только риск потери событий/задержки зачисления). Остальные маршруты — обязательно ограничиваются.
- Ответ: `HTTP 429` + заголовок `Retry-After` (остаток окна из двух вёдер берётся **max**, для фиксированного окна точный остаток через Redis `PTTL`) + тело `{code:429, message, retry_after}` (выровнено с существующим `Response::error`).
- Всплески: задействовать поле burst — `rate` это стабильная квота внутри окна, `burst` — допустимый перерасход. Реализация: предел счётчика Redis = `rate + burst` (перерасход внутри фиксированного окна), без скользящего окна (ponytail: фиксированное окно на границе даёт увеличение в 2 окна, для per-IP против злоупотреблений одного инстанса достаточно; если нужно строже — перейти на скользящее окно).
- Маппинг маршрут→правило: сохранить существующий `ROUTE_MAP`, добавить `'/graphql' => 'graphql'` (в config/security.php:46 уже есть `{rate:30, burst:5, per:60}`); неизвестные маршруты идут в `default` (60/60s).
- Недоступность Redis: сохранить существующий fail-open (catch Exception → пропустить) — грубая подстраховка nginx 100r/s остаётся.
- **Область**: только контейнер service. admin — отдельный контейнер (в nginx-admin.conf нет limit_req, сейчас без ограничений); изменения service/config и промежуточных слоёв service не затрагивают admin — ограничение admin не входит в P4.1, решается отдельно.

**D3: ограничение до аутентификации.** Глобальный промежуточный слой стоит до AuthMiddleware (порядок в middleware.php и есть порядок выполнения), поэтому per-token ведро для запросов без токена вырождается в per-IP ведро; запросы с токеном, даже по анонимным путям (например /api/products), тоже считаются в token-ведро — защита от злоупотребления общим токеном.

### Область влияния

| Пункт | Изменение |
|----|------|
| `service/common/security/RateLimitMiddleware.php` | Переработка: per-token ведро, burst, Retry-After, правило graphql |
| `service/config/middleware.php` | В список `''` добавить RateLimitMiddleware; убрать все явные точки монтирования из route.php |
| `service/config/security.php` | `default` {60,10,60} не трогать (приёмочный порог = rate+burst = 70); `graphql` {30,5,60} уже есть, добавлять не нужно; поле burst используется |
| `service/config/route.php` | Удалить ~12 явных монтирований `RateLimitMiddleware::class` (ориентироваться на фактические данные grep; группы auth/supplier/admin) |
| `docker/nginx.conf` | `limit_req` rate 10r/s → 100r/s (грубая подстраховка, чтобы поверх глобального слоя не резать бизнес) |
| Тесты | Тесты в наборе service, зависящие от явного монтирования промежуточного слоя, синхронизировать; добавить юнит-тесты промежуточного слоя |

### Приёмка (k6)

```
# Взять один анонимный маршрут (например GET /api/products) и /graphql, на каждый 200 запросов/10s:
# Выше порога ограничения — всё 429, и в ответе есть Retry-After; ниже порога — всё 200.
# Утверждение: количество 429 == всего запросов − порог; на /graphql тоже действует (бывший пробел).
```

## P4.2 Сквозная согласованность мультивалютности (включая стратегию округления fee)

### Текущее состояние (подтверждено чтением кода)

- **Хранилище**: в `install.sql` все суммы — DECIMAL —— баланс/заморозка `(16,4)`, у заказа subtotal/discount/tax/total, у строк unit_price/total_price `(12,4)`, `exchange_rate DECIMAL(12,6)` уже есть на `orders`, `payment_transactions`; `user_balances` хранит строки по валютам (учёт раздельно по валютам).
- **Источник курса**: `service/app/cron/ExchangeRateSync.php` уже реализован — внешний бесплатный API (`EXCHANGE_RATE_API_URL` env настраивается, по умолчанию exchangerate-api.com) каждый час синхронизирует в Redis `exchange_rate:{CURRENCY}`; `OrderService::getExchangeRate` при оформлении заказа читает снапшот Redis (USD всегда 1.0) и записывает в поле заказа `exchange_rate`. **Внешняя зависимость уже есть, источник сменяем через env — ничего добавлять не нужно.**
- **Проблема усечения fee**: `PaymentRouter::calculateFee` = `bcadd(bcmul($amount, $rate, 8), $fixed, 4)` —— bcmath **усекает** по scale (не округляет), направление **в недобор** <0.0001/заказ; при этом `total_amount = amount + fee` для amount с 5+ знаками после запятой (например 10.12345) после усечения может не совпадать с total заказа.
- **Проверка suspend** уже ведётся по балансам валют (мультивалютно), Billing считает по meter (цена usage_rates DECIMAL(12,4)).

### Решения

**D4: единый инвариант сумм — у каждой валюты одна внутренняя точность, округление происходит только в одной точке.**
- Внутренние расчёты единообразно `DECIMAL(12,4)` (гранулярность заказа) и `DECIMAL(16,4)` (гранулярность баланса), после любого умножения обязателен `bcround(x, 4, PHP_ROUND_HALF_UP)`, `bcadd/bcsub` — только сложение/вычитание с одинаковой точностью (сами по себе точны).
- Единственный новый помощник сумм `service/common/money/Money.php` (~40 строк):
  - `bcround(string $v, int $scale = 4, int $mode = PHP_ROUND_HALF_UP): string` — идемпотентно; у `round()` для float есть риски точности, обязателен строковый путь: `bcadd($v, '0', $scale+1)` затем по разряду $scale+1 определять HALF-UP (в реализации учесть отрицательные числа — через bccomp по abs).
  - Любое поле суммы перед записью в БД обязано пройти `bcround(…, 4)`; **запрещено** в середине цепочки вычислений использовать `(float)`/`round()` (существующий `round((float) bcmul(...))` в StripeChannel — как раз скрытая проблема).
- Существующий `calculateFee` переделать: `$fee = bcround(bcadd(bcmul(bcround($amount,4), $rate, 8), $fixed, 8), 4)` — сначала выровнять amount до 4 знаков, затем умножить на курс, затем HALF_UP до 4 знаков. **Исправление направления: недобор → стандартное полуокругление** (разница на заказ ≤0.00005, математическое ожидание стремится к 0). **Защита от отрицательного fee (прижатие к 0) сохраняется** (поведение текущего кода PaymentRouter.php:44 не меняется).

**D5: отделение тождества заказа от комиссии канала (нулевой дрейф сверки).** Два независимых факта:
- **Тождество строк заказа** `total − subtotal − tax + discount == 0` (точно до 0.0000): цепочка создания заказа (OrderService::createFromCart) — строки `bcround(bcmul(price, qty, 8), 4)` (сначала умножение с высокой точностью, затем округление — без двойного усечения) → subtotal = сумма строк (точно) → total = subtotal + tax − discount (сложение/вычитание с одинаковой точностью, точно). **tax в настоящее время всегда 0** (createFromCart не задаёт tax, в install.sql:345 DEFAULT 0.0000) — новый расчёт налога не добавляется (вне области P4.2, есть комплаенс-влияние); утверждение реализуется по текущему значению `tax=0`, но формула сохраняет член tax.
- **Комиссия канала**: channel_fee считается отдельным `bcround(…,4)`, сумма канала = total + channel_fee точно равна с точностью 4 знака.
- Проверка: `PaymentController::reconcile*` и отчёты (Report) опираются на сохранённый total заказа, не пересчитывают.

**D6: снапшот курса и точка конверсии.**
- Источник курса сохраняется: cron ExchangeRateSync + Redis (уже есть, не трогать). Колонка `exchange_rate` уже снапшотится вместе с заказом/транзакцией (DECIMAL(12,6)), **точка конверсии = расчёты (запись в БД)**, без конверсии в реальном времени при отображении (отображение текущей цены — это просто умножение в UI на текущий курс Redis, на учёт не влияет).
- Правило: **всё, что касается учёта/баланса, обязано использовать снапшот-курс заказа; всё, что касается цены/отображения, может использовать текущий курс**. Запрещено смешивать два курса в цепочке расчётов.
- Слой балансов уже ведёт раздельный учёт по валютам (user_balances по строкам currency), конвертация в единую базовую валюту не вводится; если отчёту нужна базовая валюта (например USD) — агрегировать по снапшот-курсу заказа, результат агрегации тоже проходит через `bcround(…,4)` (ponytail: ошибка округления межвалютной агрегации сидит в итоговом разряде; если последующий аудит потребует итогов по валютам — разделить).

**D7: список изменений (включая точки перепроверки существующего мультивалютного кода).**
- Изменить: `PaymentRouter::calculateFee`, `StripeChannel` (выровнять входные суммы + убрать float round, включая convertToSmallest на `bcround($total,2)`), `OrderService::createFromCart` (поразрядное округление строк/subtotal/total), **`Order/Model/Coupon.php::calculateDiscount` (:31-44 сейчас float+round, перевести на строковый путь bcround)** , `PaymentController::reconcile*` (утверждение тождества D5), `Report/*` (агрегация единообразно через bcround).
- Перепроверить без изменений: Billing meters (цена уже DECIMAL(12,4), достаточно выровнять расчёт по bcround), проверка suspend (по балансам валют, уже корректно), `Cron/ExchangeRateSync.php` (запись в Redis сохраняет 6 знаков как есть, не трогать).
- Добавить: `service/common/money/Money.php` + юнит-тесты (границы HALF_UP: 0.00005 → 0.0001, 0.00004 → 0.0000, **-0.00005 → -0.0001 (отрицательные — от нуля)** , идемпотентность).
- Миграция: структурных изменений в `install.sql` нет (колонка exchange_rate уже есть); если у исторических заказов усечение fee дало хвостовую разницу <0.0001, это необратимая разница учёта, **только запись, без починки** (проводка изменит историческую сверку), добавить аудит-запрос `fee_drift`, выводящий заказы с |total−subtotal−tax+discount|>0 для ручной проверки.

## Риски и рецензирование

- **Риск глобального ограничителя D2 (средний)**: глобальное монтирование затрагивает все эндпоинты service (**admin не затронут** — отдельный контейнер, изменения service/config его не касаются), webhook исключён; при неверном пороге — ложные срабатывания, нужна перепроверка security-auditor'ом порогов по умолчанию и стратегии fail-open. **У контейнера admin сейчас нет ограничений** (в nginx-admin.conf нет limit_req), в P4.1 не входит, решается отдельно.
- **D4/D5 денежный контур (высокий)**: изменение направления округления влияет на сумму каждого заказа (недобор → стандартное полуокругление), требуется рецензия security-auditor + перепроверка вторым человеком; исторические данные — только запись без починки.
- **Зависимости**: новых composer-зависимостей нет; новых таблиц нет; изменение nginx-конфигурации требует перезагрузки.
