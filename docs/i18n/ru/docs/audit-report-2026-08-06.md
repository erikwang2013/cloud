## 3. Критические проблемы безопасности (P0 / P1)
### P0-1. `id_token` Apple без проверки подписи — возможен прямой захват учётной записи
**Файл**: `service/app/user/service/OAuthService.php:180-192` (`appleProfile()`)

```php
$parts  = explode('.', $tokenData['id_token']);
$claims = json_decode(base64_decode($parts[1]), true);   // только base64-декодирование, без проверки подписи/iss/aud/exp
```

Атакующий может самостоятельно сформировать `id_token` и подделать любой email для входа через OAuth. `resolveUser()` сопоставляет email с существующим пользователем и сразу выдаёт токен → **захват любой учётной записи**.

**Исправление**: проверять подпись через JWKS Apple (`https://appleid.apple.com/auth/keys`) + `Firebase\JWT\JWT::decode($idToken, $keys, ['ES256'])`, а также проверять `iss=appleid.apple.com`, `aud=client_id`, `exp`, `nonce`.

### P1-1. При OAuth-входе не проверяется `email_verified`
**Файл**: `OAuthService.php:163-178, 282-303`

Google/Facebook/Microsoft/LinkedIn возвращают поле `email_verified`, код полностью его игнорирует. Пользователь с неподтверждённой почтой на стороне провайдера может напрямую привязать/захватить зарегистрированную учётную запись. В пути GitHub проверка `verified` есть (корректно), остальные провайдеры нуждаются в единой проверке.

### P1-2. Промежуточный слой ограничения частоты существует, но нигде не смонтирован — документация расходится с реализацией
**Файл**: `common/Security/RateLimitMiddleware.php` + `config/security.php` + `config/route.php`

- В `security.php` настроены правила: login=5/мин, register=3/мин и др.
- `RateLimitMiddleware` **не используется ни одним маршрутом** (grep по всей базе находит только сам класс)
- `docs/features.md` утверждает «ограничение входа 5 req/min», «регистрации 3 req/min» — фактически отсутствует
- Исторический отчёт о проверке (`security-audit-2026-08-04.md`) помечал этот пункт OK — проверялась только конфигурация без проверки монтирования; в этом раунде исправлено

**Влияние**: публичные эндпоинты входа/регистрации/восстановления пароля/сброса пароля/кодов восстановления/капчи можно перебирать без ограничения (вход защищён только блокировкой per-account, не защищает от подбора по базе и IP-флуда).

**Исправление**: смонтировать `RateLimitMiddleware` на публичные маршруты `/api/auth/*`, `/api/captcha/*` и т.п. (можно повесить на глобальную группу `''`, различая по параметру `route`).

### P1-3. TOTP 2FA не принудительно применяется в процессе входа
**Файл**: `AuthService.php:64-97` (`login()`) + `AuthController.php` + `config/features.php`

`user->totp_enabled` проверяется только в `totpVerify/totpDisable/totpRecoveryCodes`, **`login()` не проверяет его никогда**. Пользователь с включённой 2FA по-прежнему получает действующий access token только по паролю — 2FA не работает (`FEATURE_TOTP` включён по умолчанию).

**Исправление**: при входе, если `totp_enabled`, выдавать временный токен и требовать успешную проверку TOTP для обмена на полноценный токен (или требовать параметр totp code).

### P1-4. Каналы уведомлений — заглушки: подтверждение почты/сброс пароля в проде недоступны
**Файл**: `app/Notification/Queue/EmailSender.php`, `SmsSender.php`, `PushSender.php`

Все три потребителя только имитируют отправку через `error_log()` и помечают `send_status` как `sent`. Последствия:
- **Разрыв цепочки восстановления пароля**: `AuthController::forgotPassword()` генерирует код и «отправляет» письмо, но письмо никогда не доставляется → пользователь не может самостоятельно сбросить пароль
- Подтверждение почты при регистрации, предупреждения о входе с нового IP — аналогично не работают
- Переменные `SMTP_*`/`MAIL_FROM_*` (всего 7) из `.env.example` не читаются ни одним кодом (мёртвая конфигурация)

**Исправление**: подключить реальную отправку почты (PHPMailer/SendGrid SDK), убрать вводящий в заблуждение статус `sent`; или явно пометить как незавершённую функцию и удалить связанные обещания из документации.

## 6. Рекомендации по оптимизации (неблокирующие)
1. **Создание сервисов через DI**: конструктор `AuthController` напрямую делает `new AuthService()/OAuthService()`, рекомендуется подключить контейнер (webman поддерживает нативно) — удобнее тестировать и заменять.
2. **Укрепление каталога загрузок**: разместить в каталоге `index.html`, запретить выполнение PHP (nginx `location ~ \.php { deny all; }`).
3. **Сужение WAF-регулярок**: `sqli_patterns` в `security.php` содержат широкие паттерны типа `\b(select|update|delete|...)\b`; при глобальном ограничении появление этих слов в тикетах/отзывах пользователей даст ложное 403; рекомендуется применять только к чувствительным параметрам или ужесточить регулярки.
4. **Журнал аудита**: `AuditLogger::record('user_registered', ['user_id' => null])` не фиксирует ID нового пользователя, рекомендуется регистрировать фактический ID.
5. **Тестовое покрытие OAuth**: `OAuthServiceTest` покрывает построение URL и обмен code, но `resolveUser()` (путь БД) и путь проверки подписи Apple без тестов; после исправления P0 обязательно добавить тестовые случаи провала проверки подписи.
6. **Подключение CI**: в проекте есть каталог `.github`, рекомендуется добавить GitHub Actions: `composer install && phpunit` + `composer audit`, чтобы предотвратить регрессии.
7. **Ограничение HTTP-методов**: одновременная регистрация callback GET/POST для OAuth-маршрутов оправдана (требуется Apple), остальные публичные операции записи явно POST, OK.
