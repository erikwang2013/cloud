## P4.1 স্বাধীন API গেটওয়ে + ইউনিফাইড রেট লিমিট

### বর্তমান অবস্থা (সরাসরি পড়ে নিশ্চিত)

| স্তর | বর্তমান অবস্থা |
|----|------|
| এজ গেটওয়ে | docker/nginx.conf service-এর L7 গেটওয়ে: `limit_req_zone api 10r/s` (গ্লোবাল রেট লিমিট), proxy_pass 8787 (service), 8282 (ws)। **admin আলাদা কন্টেইনার** (Dockerfile admin target, nginx-admin.conf listen 8788 proxy 8788), **limit_req নেই** |
| অ্যাপ রেট লিমিট | `service/common/security/RateLimitMiddleware.php` আগে থেকেই আছে: Redis INCR+expire ফিক্সড উইন্ডো, **শুধু per-IP**, `ROUTE_MAP` অনুযায়ী রুল নির্বাচন, **এক্সপ্লিসিট রাউটে** লাগানো (route.php-এ মোট ~১২ জায়গা) |
| রুল কনফিগ | `config/security.php rate_limits`: default/login/register/password_reset/oauth/captcha/sms/pay/upload/supplier_api/graphql, সবগুলোতে rate/burst/per আছে, কিন্তু **burst ফিল্ড বর্তমানে ব্যবহৃত হয় না** |
| গ্লোবাল মিডলওয়্যার | `config/middleware.php` `''` কী সব রাউটে কার্যকর সাপোর্ট করে (WAF/GeoBlock/Security ইত্যাদি ১০টি এখানে) |
| ঘাটতি | `/graphql` (public + authenticated দুটি রাউট) **কোনো রেট লিমিট নেই**; per-token রেট লিমিট নেই; 429 রেসপন্সে `Retry-After` হেডার নেই; webhook-এ এক্সেম্পশন/নির্দিষ্ট রুল নেই |

### সিদ্ধান্ত

**D1: নতুন আলাদা গেটওয়ে প্রসেস তৈরি করা হবে না।** nginx-ই গেটওয়ে (নেটওয়ার্ক এজ + রেট লিমিট + রাউট স্প্লিট), webman-এর ভিতরে ইউনিফাইড রেট লিমিট।
- কারণ: আলাদা gateway কন্টেইনারে নতুন ডিপেন্ডেন্সি/নতুন ডিপ্লয়মেন্ট টপোলজি/ডাবল অথেনটিকেশন লাগত, বর্তমান সিঙ্গেল-ইন্সট্যান্স স্কেলে এটা ওভার-ইঞ্জিনিয়ারিং;
- ট্রেড-অফ: গেটওয়ে লেয়ারে per-token/per-রাউট ডিফারেন্সিয়েটেড রেট লিমিট করা যায় না (nginx-এ শুধু per-IP জোন আছে)। ডিফারেন্সিয়েশন অ্যাপ লেয়ার দিয়ে পূরণ হয়, nginx লেয়ার শুধু কোয়ার্স-গ্রেইন্ড IP ফলব্যাক রাখে (বর্তমান 10r/s বাড়িয়ে 100r/s করা হবে যাতে বিজনেস ভুলবশত ব্লক না হয়, k6 ভেরিফিকেশনের সময় ডেমো থ্রেশহোল্ডে ফিরিয়ে আনা হবে)।
- ইভোল্যুশন পাথ: ভবিষ্যতে মাল্টি-ইন্সট্যান্স/মাল্টি-সার্ভিস হলে, `config/middleware.php`-এর গ্লোবাল রেট লিমিটার অপরিবর্তিতভাবে আলাদা gateway সার্ভিসে নিয়ে যাওয়া যাবে, মিডলওয়্যার ডিপ্লয়মেন্ট ফর্ম সম্পর্কে অবগত নয়।

**D2: ইউনিফাইড রেট লিমিট = গ্লোবাল মিডলওয়্যার + ডুয়াল-ডাইমেনশন বালতি (per-IP + per-token)।**
- `RateLimitMiddleware` এক্সপ্লিসিট রাউট থেকে সরিয়ে (route.php-এ আসলে ~১২ জায়গা, grep দিয়ে নিশ্চিত), `config/middleware.php` `''` গ্লোবাল লিস্টে মাউন্ট (WAF-এর পরে, বিজনেস মিডলওয়্যারের আগে), **স্বাভাবিকভাবে অ্যাপের সব রাউট কভার করে (graphql-এর দুটি রাউট সহ)**।
- **বালতি সেম্যান্টিক্স (স্পষ্ট, বাইপাস প্রতিরোধ)**: `ratelimit:ip:{realIp}:{rule}` ও `ratelimit:tok:{sha256(token)}:{rule}` দুটি বালতি স্বাধীনভাবে কাউন্ট হয়, **যেকোনো একটি বালতি ওভার হলে 429 (OR)**। AND বাস্তবায়ন নিষিদ্ধ — AND-তে IP বদলালে per-IP বালতি বাইপাস হয়, token বদলালে per-token বালতি বাইপাস হয়।
- **এক্সেম্পশন লিস্ট**: `/health*` (মনিটরিং প্রোব) ও `/api/payments/webhook/stripe` (সিগনেচার ভ্যালিডেশন আসল ডিফেন্স + Stripe 429 অটো ব্যাকঅফ রিট্রাই + nginx কোয়ার্স 100r/s ফলব্যাক কার্যকর থাকে; রেট লিমিটে কোনো সিকিউরিটি লাভ নেই, শুধু ইভেন্ট হারানো/বিলম্বিত পেমেন্টের ঝুঁকি)। বাকি সব রাউটে অবশ্যই রেট লিমিট।
- রেসপন্স: `HTTP 429` + `Retry-After` হেডার (দুই বালতির উইন্ডো বাকি থেকে **max** নেওয়া হয়, ফিক্সড উইন্ডোতে Redis `PTTL` দিয়ে সঠিক অবশিষ্ট) + body `{code:429, message, retry_after}` (বর্তমান `Response::error` ফরম্যাটের সাথে মিলিয়ে)।
- বর্স্ট: burst ফিল্ড সক্রিয় — `rate` উইন্ডোর স্টেডি-স্টেট কোটা, `burst` ওভারড্রাফট কোটার অনুমতি। বাস্তবায়ন: Redis কী কাউন্ট সীমা `rate + burst` (ফিক্সড উইন্ডোর মধ্যে ওভারড্রাফট), স্লাইডিং উইন্ডো প্রয়োজন নেই (ponytail: ফিক্সড উইন্ডো বাউন্ডারিতে ২ গুণ উইন্ডো এমপ্লিফিকেশন আছে, সিঙ্গেল-মেশিন অ্যাবিউজের জন্য per-IP যথেষ্ট; কঠোর দরকার হলে স্লাইডিং উইন্ডোতে বদলানো যাবে)।
- রাউট→রুল ম্যাপিং: বর্তমান `ROUTE_MAP` রাখা হবে, `'/graphql' => 'graphql'` যোগ হবে (config/security.php:46-এ আগেই `{rate:30, burst:5, per:60}` আছে); অজানা রাউট `default` (60/60s) নেবে।
- Redis অনুপলব্ধ: বর্তমান fail-open (catch Exception দিয়ে পাস) বহাল — nginx 100r/s কোয়ার্স ফলব্যাক এখনও আছে।
- **সুযোগ**: শুধু service কন্টেইনার। admin আলাদা কন্টেইনার (nginx-admin.conf-এ limit_req নেই, বর্তমানে রেট লিমিট নেই), service/config ও service মিডলওয়্যার পরিবর্তন admin-কে প্রভাবিত করে না — admin রেট লিমিট P4.1-এর সুযোগের বাইরে, আলাদা সিদ্ধান্ত।

**D3: অথেনটিকেশনের আগে রেট লিমিট।** গ্লোবাল মিডলওয়্যার AuthMiddleware-এর আগে (middleware.php-এর ক্রমই এক্সিকিউশন ক্রম), তাই token ছাড়া রিকোয়েস্টে per-token বালতি per-IP বালতিতে ডিজেনারেট হয়; tokenসহ রিকোয়েস্ট অ্যানোনিমাস পাথ হলেও (যেমন /api/products) token বালতিতে কাউন্ট হয় — শেয়ারড টোকেন অ্যাবিউজ প্রতিরোধ।

## P4.2 মাল্টি-কারেন্সি ফুল চেইন কনসিস্টেন্সি (fee রাউন্ডিং স্ট্র্যাটেজি সহ)

### বর্তমান অবস্থা (সরাসরি পড়ে নিশ্চিত)

- **স্টোরেজ**: `install.sql`-এ সব অ্যামাউন্ট DECIMAL —— ব্যালেন্স/ফ্রোজেন `(16,4)`, অর্ডার subtotal/discount/tax/total, লাইন আইটেম unit_price/total_price `(12,4)`, `exchange_rate DECIMAL(12,6)` আগে থেকেই `orders`, `payment_transactions`-এ; `user_balances` কারেন্সি অনুযায়ী আলাদা সারি (কারেন্সিভিত্তিক হিসাব)।
- **এক্সচেঞ্জ রেট সোর্স**: `service/app/cron/ExchangeRateSync.php` আগে থেকেই আছে — এক্সটার্নাল ফ্রি API (`EXCHANGE_RATE_API_URL` env দিয়ে কনফিগারযোগ্য, ডিফল্ট exchangerate-api.com) প্রতি ঘণ্টায় Redis `exchange_rate:{CURRENCY}`-এ সিঙ্ক করে; `OrderService::getExchangeRate` অর্ডারের সময় Redis স্ন্যাপশট পড়ে (USD সবসময় 1.0) অর্ডারের `exchange_rate` ফিল্ডে লেখে। **এক্সটার্নাল ডিপেন্ডেন্সি আগেই আছে ও env দিয়ে সোর্স বদলানো যায়, নতুন লাগবে না।**
- **fee ট্রানকেশন সমস্যা**: `PaymentRouter::calculateFee` = `bcadd(bcmul($amount, $rate, 8), $fixed, 4)` —— bcmath scale অনুযায়ী **ট্রানকেট** করে (রাউন্ড নয়), দিক **কম আদায়** <0.0001/অর্ডার; আর `total_amount = amount + fee` ৫+ দশমিকের amount-এর (যেমন 10.12345) জন্য ট্রানকেশনের পর অর্ডার total-এর সাথে অসামঞ্জস্যপূর্ণ হতে পারে।
- **suspend চেক** কারেন্সিভিত্তিক ব্যালেন্স দিয়ে হয় (মাল্টি-কারেন্সি), Billing meter অনুযায়ী বিল করে (usage_rates ইউনিট প্রাইস DECIMAL(12,4))।

### সিদ্ধান্ত

**D4: ইউনিফাইড অ্যামাউন্ট ইনভেরিয়েন্ট — প্রতিটি কারেন্সির জন্য একটি ইন্টারনাল প্রিসিশন, রাউন্ডিং শুধু একক পয়েন্টে।**
- ইন্টারনাল হিসাব ইউনিফর্ম `DECIMAL(12,4)` (অর্ডার গ্রানুলারিটি) ও `DECIMAL(16,4)` (ব্যালেন্স গ্রানুলারিটি), সব গুণনের পরে অবশ্যই `bcround(x, 4, PHP_ROUND_HALF_UP)`; `bcadd/bcsub` শুধু একই প্রিসিশনে যোগ/বিয়োগ (সেটা নিজেই সুনির্দিষ্ট)।
- নতুন একমাত্র অ্যামাউন্ট হেল্পার `service/common/money/Money.php` (প্রায় ৪০ লাইন):
  - `bcround(string $v, int $scale = 4, int $mode = PHP_ROUND_HALF_UP): string` —— ইডেম্পোটেন্ট; `round()` ফ্লোটে প্রিসিশন ঝুঁকি আছে, অবশ্যই স্ট্রিং পথ: `bcadd($v, '0', $scale+1)` তারপর $scale+1তম স্থান দেখে HALF-UP সিদ্ধান্ত (বাস্তবায়নে ঋণাত্মক সংখ্যা হ্যান্ডলিং খেয়াল রাখুন, bccomp দিয়ে abs যাচাই করলেই হয়)।
  - যেকোনো অ্যামাউন্ট ফিল্ড DB-তে লেখার আগে অবশ্যই `bcround(…, 4)`; হিসাব চেইনের মাঝে `(float)`/`round()` **নিষিদ্ধ** (বর্তমান StripeChannel-এর `round((float) bcmul(...))`-ই ঝুঁকিপূর্ণ)।
- বর্তমান `calculateFee` পরিবর্তন: `$fee = bcround(bcadd(bcmul(bcround($amount,4), $rate, 8), $fixed, 8), 4)` —— আগে amount-কে ৪-স্থানে অ্যালাইন, তারপর রেট গুণ, তারপর HALF_UP ৪-স্থানে। **দিক সংশোধন: কম আদায় → স্ট্যান্ডার্ড হাফ-রাউন্ড** (প্রতি অর্ডার পার্থক্য ≤0.00005, প্রত্যাশিত মান 0-এর দিকে)। **ঋণাত্মক fee ০-তে ক্ল্যাম্প করা সুরক্ষা বহাল** (বর্তমান কোড PaymentRouter.php:44-এর আচরণ অপরিবর্তিত)।

**D5: অর্ডার আইডেন্টিটি ও চ্যানেল ফি আলাদা (রিকনসিলিয়েশন জিরো-ড্রিফট)।** দুটি স্বাধীন সত্য:
- **অর্ডার লাইন আইডেন্টিটি** `total − subtotal − tax + discount == 0` (0.0000 পর্যন্ত সুনির্দিষ্ট): অর্ডার তৈরির চেইনে (OrderService::createFromCart) লাইন আইটেম `bcround(bcmul(price, qty, 8), 4)` (আগে উচ্চ-প্রিসিশন গুণ তারপর রাউন্ড, ডাবল ট্রানকেশন এড়াতে) → subtotal = লাইনগুলোর যোগফল (সুনির্দিষ্ট) → total = subtotal + tax − discount (একই প্রিসিশনের যোগ/বিয়োগ, সুনির্দিষ্ট)। **tax বর্তমানে সবসময় 0** (createFromCart tax সেট করে না, install.sql:345 DEFAULT 0.0000) — নতুন ট্যাক্স হিসাব যোগ নয় (P4.2-এর সুযোগের বাইরে, কমপ্লায়েন্স প্রভাব আছে), অ্যাসার্ট বর্তমান `tax=0` মান দিয়ে বাস্তবায়িত কিন্তু ফর্মুলায় tax টার্ম থাকে।
- **চ্যানেল ফি**: channel_fee স্বাধীন `bcround(…,4)`, পেমেন্ট চ্যানেল অ্যামাউন্ট = total + channel_fee 4dp-তে সুনির্দিষ্ট সমান।
- ভ্যালিডেশন: `PaymentController::reconcile*` ও রিপোর্ট (Report) অর্ডারে সংরক্ষিত total-কে বেস ধরে, পুনরায় হিসাব করে না।

**D6: এক্সচেঞ্জ রেট স্ন্যাপশট ও কনভার্সন পয়েন্ট।**
- রেট সোর্স ExchangeRateSync cron + Redis বহাল (আগেই আছে, বদলানো হয় না)। `exchange_rate` কলাম অর্ডার/ট্রানজেকশনের সাথে স্ন্যাপশট হয় (DECIMAL(12,6)), **কনভার্সন পয়েন্ট = সেটেলমেন্ট (DB-তে লেখা) সময়**, ডিসপ্লেতে রিয়েল-টাইম কনভার্সন নয় (ডিসপ্লে রিয়েল-টাইম প্রাইস শুধু UI লেয়ারে বর্তমান Redis রেট দিয়ে গুণ, বইয়ে প্রভাব নেই)।
- নিয়ম: **বই/ব্যালেন্স সংশ্লিষ্ট হলে অবশ্যই অর্ডার স্ন্যাপশট রেট; প্রাইসিং/ডিসপ্লে হলে বর্তমান রেট ব্যবহার করা যাবে**। সেটেলমেন্ট চেইনে দুটি রেট মেশানো নিষিদ্ধ।
- ব্যালেন্স লেয়ার আগে থেকেই কারেন্সিভিত্তিক লেজার (user_balances কারেন্সি অনুযায়ী সারি), ইউনিফাইড বেস-কারেন্সি কনভার্সন নেই; রিপোর্টে বেস কারেন্সি (যেমন USD) দরকার হলে অর্ডার স্ন্যাপশট রেট দিয়ে সামারি, সামারি ফলাফলও `bcround(…,4)` (ponytail: ক্রস-কারেন্সি সামারির রাউন্ডিং এরর সমষ্টি স্থানে, ভবিষ্যতে অডিটে কারেন্সিভিত্তিক সমষ্টি চাইলে ভেঙে নেওয়া যাবে)।

**D7: পরিবর্তন তালিকা (বিদ্যমান মাল্টি-কারেন্সি কোড রিভিউ পয়েন্ট সহ)।**
- পরিবর্তন: `PaymentRouter::calculateFee`, `StripeChannel` (অ্যামাউন্ট ইনপুট অ্যালাইন + float round অপসারণ, convertToSmallest-ও bcround($total,2)), `OrderService::createFromCart` (লাইন আইটেম/subtotal/total ক্রমিক রাউন্ড), **`Order/Model/Coupon.php::calculateDiscount` (:31-44 বর্তমানে float+round, bcround স্ট্রিং পাথে পরিবর্তন)** , `PaymentController::reconcile*` (D5 আইডেন্টিটি অ্যাসার্ট), `Report/*` (সামারি ইউনিফর্ম bcround)।
- রিভিউ করে অপরিবর্তিত: Billing meters (ইউনিট প্রাইস আগেই DECIMAL(12,4), বিলিং bcround দিয়ে অ্যালাইন করলেই), suspend চেক (কারেন্সিভিত্তিক ব্যালেন্স যাচাই, আগেই সঠিক), `Cron/ExchangeRateSync.php` (Redis-এ ৬-স্থান অরিজিনাল লেখা, অপরিবর্তিত)।
- নতুন: `service/common/money/Money.php` + ইউনিট টেস্ট (HALF_UP বাউন্ডারি: 0.00005 → 0.0001, 0.00004 → 0.0000, **-0.00005 → -0.0001 (ঋণাত্মক শূন্য থেকে দূরে)** , ইডেম্পোটেন্সি)।
- মাইগ্রেশন: `install.sql`-এ কোনো স্ট্রাকচার পরিবর্তন নেই (exchange_rate কলাম আগেই আছে); ঐতিহাসিক অর্ডারে fee ট্রানকেশন <0.0001 টেইল-ডিফারেন্স তৈরি থাকলে, সেটা বইয়ের অপরিবর্তনীয় পার্থক্য, **শুধু রেকর্ড করা হবে, প্যাচ করা হবে না** (একটি এন্ট্রি ঠিক করলে ঐতিহাসিক রিকনসিলিয়েশন বদলে যাবে), নতুন অডিট কুয়েরি `fee_drift` |total−subtotal−tax+discount|>0 এমন অর্ডার তালিকাভুক্ত করবে ম্যানুয়াল চেকের জন্য।
