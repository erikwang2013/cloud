## 3. ブロッキング問題（依存順）

### B1. ENCRYPTION_MASTER_KEY の形式がコード要件と不一致 → admin worker が起動直後にクラッシュ
- **現象**：`php start.php start` 後、4 つの worker がすべて例外で終了（ポートは開いているがリクエストが永遠に応答せず、accept backlog に接続が滞留）。ログ：
  `InvalidArgumentException: Master key must be exactly 32 bytes. in vendor/erikwang2013/encryption/src/EncryptionManagerFactory.php:29`
- **根本原因**：`admin/.env` の `ENCRYPTION_MASTER_KEY=y1Odnbg50NHEvvLHGb8aexKqy8AQ7izm0x+yoEgrYCU=` は **44 バイトの base64**。一方 `EncryptionManagerFactory::fromMasterKey()` は **32 バイトの生バイト**を要求（`admin/config/encryption.php:30` のコメントも「64 hex characters」と記載）。しかし `.env.example:64` は base64 と表記——設定とコードの約束事が矛盾。
- **補足**：`support/bootstrap.php:47` は `Dotenv::createUnsafeMutable()->load()` を使用しており、**プロセスレベルの env 上書きは .env の値に上書きされる**ため、起動パラメータでは回避できない（実測 2 回とも失敗）。
- このキーの base64 デコード結果はちょうど 32 バイト（hex `cb539d9d…6025`）。つまり正しい形式 = base64 デコード後の値。

### B2. `config/database.php` 欠落 → データベース層が存在しない
- **現象**：`/account/login` → 500 `BusinessException: 请重启webman`（`app/controller/AccountController.php:263` の `checkDatabaseAvailable()` で、`!config('database')` なら即 throw）。
- **根本原因**：このファイルはインストールウィザードが生成し gitignore されているため、リポジトリには元々存在しない（`git ls-files` に記録なし）。`config/thinkorm.php` も同様に欠落。

### B3. `install.sql` 欠落 → インストールウィザードが実行不能
- **現象**：ウィザードの `step1`（`InstallController.php:105`）が `base_path().'/install.sql'` をチェックし、欠落なら「数据库SQL文件不存在」を返す。ファイルはリポジトリに存在しない。
- 影響：B2 を修正する唯一の公式パス（UI ウィザード）も通れない。

### B4. 全ビューの静的リソースパスが `/app/admin/` プレフィックスを使用するが、そのプレフィックスにマッピングが一切ない → UI 全体にスタイルなし、JS 404
- **現象**（ログインページ/インストールページ/メインフレームで実測）：`/app/admin/component/pear/css/pear.css`、`/app/admin/admin/css/reset.css`、`/app/admin/component/layui/layui.js` などがすべて 404。`ReferenceError: layui is not defined`。フォームが送信不能。
- **根本原因**：静的ファイルは実際には `public/admin/`、`public/component/` にあり（webman が `/admin/...` で提供、実測 200）。一方 `app/view/account/login.html`、`app/view/index/install.html`、`app/view/index/index.html` などはすべて `/app/admin/...` を参照。`config/route.php` の明示的な `/app/admin/` ルートは 4 本のみ（captcha/dict/dashboard-data/table-export）。`config/static.php` にプレフィックスマッピングなし。`docker/nginx.conf` と `docker/nginx-admin.conf` にも `location /app/admin` なし。フロントエンドとバックエンドの URL 約束事が全体として不一致（フォーム POST `/app/admin/account/login` → 404。実際のエンドポイントはルート `/account/login` であるべき）。

### B5. 未ログインのリダイレクト先が誤り → 業務ページがすべて Chrome 404 ページに
- **現象**（/user/index、/order/index、/product/index、/supplier/index、/config/index、/role/index、/admin/index、/ticket/index、/index/dashboard、/dashboard/index で実測）：200 を返すが、ページは JS で `http://127.0.0.1:8788/app/admin` にリダイレクト → その URL は 404 → Chrome の「ページが見つかりません」が描画。
- **根本原因**：`app/middleware/AccessControl.php:45` の未ログイン時は `admin_error_401_script()`（`app/functions.php:93`）を返す。その内容は `<script>top.location.href = '/app/admin';</script>`——ログインページのアドレスが `/app/admin` にハードコードされ、B4 と同源のパス約束事エラー。
- 付随：`/payment_channel/index`、`/coupon/index`、`/domain_tld/index`、`/dns_zone/index`、`/invoice/index`、`/report/index` は直接 `ERR_HTTP_RESPONSE_CODE_FAILURE`（コントローラー/ルート層で失敗し、リダイレクトまで到達しない）。

### B6. ルートパス 500：`system_config` データ欠落
- **現象**：B2 の設定を手動で補完した後、`GET /`（ログインページ描画エントリ `IndexController::index`）→ 500 `ErrorException: json_decode(): Passing null to parameter #1 … in app/controller/IndexController.php:49`。
- **根本原因**：`Option::where('name','system_config')->value('value')` が null を返す（DB に行がない——本 DB はウィザードでインストールされたものではない）、PHP 8.3 で `json_decode(null)` が deprecation を発火して例外になる。つまりログインページはデータがウィザード通りに初期化されていないと即クラッシュする。

## 5. 発見した UI 欠陥のまとめ

### 第 1 ラウンド（環境の現状のまま、ブロッキング）

1. **B1（ブロッキング）** `.env` のマスターキー base64 がコードの 32 バイト要件と不一致 → サービスが完全に起動しない。再現：`cd admin && php start.php start -d`。
2. **B2/B3（ブロッキング）** インストール成果物の欠落（config/database.php、install.sql）、かつウィザード自体が実行不能 → アプリを初期化できない。
3. **B4（ブロッキング）** 全サイトのビューリソースパス `/app/admin/...` が静的ファイルの実位置/ルートプレフィックスと不一致 → スタイルなし、JS なし、フォーム使用不可。
4. **B5（ブロッキング）** 未ログイン 401 リダイレクトが `/app/admin` にハードコード → 全業務ページが死リンクに飛ぶ。
5. **B6** ログインページ描画に `system_config` 行欠落のフォールバックがなく、`json_decode(null)` で直接 500（PHP 8.3 の deprecation が例外に昇格）。

### 第 2 ラウンド（ログイン後実測、系統的問題）

6. **W1. WAF が業務 URL を誤殺**：`admin/app/middleware/WafMiddleware.php:75` が URL path に SQLi/XSS 正規表現スキャン（`config/security.php`：`\b(union|select|insert|update|delete|drop|...)\b`、`\balert\b` など）を実施：
   - `/alert/index` は URL に "alert" が含まれ XSS ルールにヒット → **403**；
   - 全 CRUD データエンドポイント（`/user/select`、`/user/insert`、`/user/update`、`/user/delete`、`/order/select`…）が `\bselect\b` などの SQLi ルールにヒット → **403**。
   - 影響：**すべての一覧ページのデータ読み込みと追加・削除・変更がブラウザで完全に使用不可**（フロントエンドの `SELECT_API` リクエストがすべて 403）。
7. **W2. URL アンダースコアの約束事が成立しない + メニューリンク全滅**：webman の自動ルーティングはコントローラー名のアンダースコアをサポートしない——`/order_item/index` は 404、`/orderitem/index` は 200（47 ページすべて camelCase 連結の URL で到達可能）。しかし `config/menu.php` と `config/business_menu.php` の全 href は `/app/admin/<snake_case>/index`（例：`/app/admin/payment_channel/index`）→ **サイドナビゲーションのすべての項目が死リンク（404 または 403）**。
8. **W3. テーブルデータ JS 定数 SELECT_API が未定義**：ページ JS（`/app/admin/...` 404、B4 の残滓）が参照する `SELECT_API`/`INSERT_API` などの定数が注入されていない → 一覧ページのテーブル描画にデータなし、ページング/検索不能。
9. **W4. 各ページ 11〜15 の静的リソース 404 コンソールエラー**：B4 の持続的影響面——47 の 200 ページすべてスタイルなし、`layui is not defined`、フォームとモーダル使用不可。

**まとめ**：ページの骨格は描画可能（47/51）だが、サイドナビゲーション（W2）、テーブルデータ読み込み（W3+W1）、全 CRUD 書き込み操作（W1）はブラウザで使用不可——バックエンドは実質操作不能。

## 6. 未テストページと原因

- **CRUD 書き込み操作（新規/編集/削除のフォーム送信）**：データエンドポイントがすべて WAF にブロック（W1）+ フォーム JS 使用不可（B4/W3）のため、UI 経由の書き込み操作は一切完了不可。W1 と B4 を修正すれば、`insert/update/delete` エンドポイントで補テスト可能。
- **ログイン後のページ**：第 2 ラウンドで全実測済み（47/51 描画成功、§4.2 参照）。未カバーはメニュー遷移（W2 死リンク）とテーブルデータ読み込み（W1/W3）のみ。
- **apps/（Flutter/HarmonyOS クライアント）**：実機/エミュレータが必要。今回の範囲外（タスクの取り決めどおり Web にフォーカス）。
- **service 業務 API ページ**：Web UI なし（8787 の `/` と `/install.php` はどちらも 404、純 API）。インターフェースレベルのテストはタスク #13 でカバー。

## 7. 現在の環境状態と修正提案

- **テスト DB の変更（ユーザー承認済み、注意が必要）**：
  - `wa_admins` のアカウント `admin` のパスワードは**一時的に `Test@123456` にリセット済み**（ローカルテスト DB のみ）。ユーザーは早急に戻すこと；
  - `wa_options` に `system_config` 行を追加（B6 修正、テスト DB 操作）。
- 現在の 8788 は `/tmp/cp-admin-ui` コピーインスタンスが提供（bootstrap は通る、DB は接続済み）。リポジトリの元インスタンスは停止済み（worker が起動即クラッシュ）。コピーの差分は：`/tmp/cp-admin-ui/.env` のマスターキーを 32 バイトの生値に変更；`config/database.php`/`thinkorm.php` を生成（同じ `cloud_platform` DB を参照）。**リポジトリのネイティブサービスを復元する場合：先に B1（.env のマスターキーをデコード後の 32 バイトに変更）、次に /tmp インスタンスを停止してからリポジトリインスタンスを起動。**
- 修正優先度の提案：B1（.env の 1 行変更）→ B2/B3（インストール成果物の補完/実行）→ B4/B5（ビューとリダイレクト URL プレフィックスの統一、または `/app/admin` 静的マッピングの追加）→ B6（Option 欠落のフォールバック）→ W1（WAF をリクエストボディ/パラメータのみのスキャンに変更し、URL path と単語のみのコントローラー名をスキップ）→ W2（メニュー href を `/{controller}/index` のプレフィックスなし形式に変更、ついでにアンダースコアを除去）。
- 注意：`.env` が git にある場合（本リポジトリにはコミット記録あり）は .gitignore に追加すべき。マスターキーはリポジトリ内の平文ではなく env 注入を推奨。
