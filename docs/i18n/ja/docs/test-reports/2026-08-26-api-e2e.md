## アプリケーション欠陥（現在コード、再現済み）

### 欠陥 1：encryptable データベースフィールド暗号化のキー長誤り → 全暗号化フィールドの書き込みが 500
- 現象：`POST /api/auth/register`、`POST /api/auth/login`（正しいパスワード）、`POST /api/auth/refresh`、`POST /api/user/addresses` がすべて HTTP 500 `Server internal error` を返す（register は暗号化チャネルで 200 + payload にラップされるが、復号後も同様に `Server internal error`）。
- 根本原因：`.env` の `ENCRYPTION_CIPHER=aes-128-ecb`（16 バイトキーが必要）+ `ENCRYPTION_KEY=YKBEUxiX/G8HwVS4S+/UxQ==`（base64 エンコードされた 16 バイトだが、コードが base64_decode せずに使用するため実長 24 文字）→ `vendor/erikwang2013/encryptable/src/Encrypter.php:74` が `MissingEncryptionKeyException: The encryption key must be 16 bytes for cipher [aes-128-ecb]` を投げる。
- 影響面：`Encryptable` cast を持つ全モデルの書き込み：users（email/phone/password_hash）、refresh_tokens（token_hash/device_fingerprint）、user_addresses（phone/address）、user_kyc、payment_channels、suppliers、host_machines、provider_api。すなわち登録、ログインの token 発行、token リフレッシュ、住所追加がすべて使用不可。
- 修正提案：`config/encryptable.php` で `ENCRYPTION_KEY` を `base64_decode` する（または .env に 16 バイトの平文キーを直接置く）。
- テスト処理：ログイン後の token はテストスクリプトが `JwtAuth::issueAccessToken`（同一キー）を直接呼んで発行し、以降のチェーンを接続。登録/ログイン/リフレッシュ/住所作成は欠陥プローブでアサート（PASS = 欠陥確認済み。修正後はこのアサートが FAIL に転じリグレッションを通知）。

### 欠陥 2：admin モデルが `erik_*` テーブルにマッピング（リポジトリのマイグレーションにない）→ テーブル欠落時は CRUD 全滅 / テーブル存在時は service とデータ分断
- 現象：`admin/app/model/*.php` のすべてが `protected $table = 'erik_*'` を宣言。テスト期間中に 2 形態を観測：
  1. erik_* テーブル不存在（現在の DB 状態、erik_* テーブルは並行環境変動で削除済み）：9/12 の admin `/select` データエンドポイントが `code=42 SQLSTATE[42S02] ... Table 'cloud_platform.erik_orders/erik_products/...' doesn't exist` を返す。`/insert` も同様に 42。実テーブルにマッピングする user/role/audit_log のみ利用可能（user→users、role→wa_roles）。
  2. erik_* テーブルが手動作成された場合（テスト中盤に別 agent が建表し一時的に存在）：admin の `/select`、`/insert`、`/delete` はすべて code=0 で利用可能だが、書き込みは `erik_products` に落ち、service は `products` のみ読む → admin が作成した製品はショップ一覧に表示されない（プローブアサート listed=n で確認、修正後は FAIL に転じリグレッションを通知）。
- 付記（観測異常）：E2E 全量実行時に `POST /app/admin/product/insert` レスポンスの id(hashid) が実際の落庫行 id と不一致（例：レスポンス nE6vQwlYejMd→350964708271980544 vs 実行 350963879578173440）。レスポンス id で delete を呼ぶと code=0 だが一致行がなく、静かに空削除される（全量実行 2 回とも再現）。単独プローブ（ログイン直後に insert）では再現せず、リクエストタイミング/スノーフレーク ID 生成に関係する疑い。深掘りは未実施。テストスクリプトは slug で実際の行 id を再照会して削除/クリーンアップに使用するよう変更済み。
- 影響面：admin パネルとショップフロントのデータチェーンが分断（admin が管理するデータはショップで見えず、逆も同様）。insert レスポンスの id が信頼できないと、クライアントの削除/更新が静かに失敗する。
- 修正提案：admin 各モデルの `$table` から `erik_` プレフィックスを外し、service の実テーブルに統一（マイグレーション/シードも補完）；insert レスポンス id の生成チェーンを調査。
- テスト処理：一覧は欠陥プローブでアサート（code=0 または SQL 1146 どちらでも PASS=欠陥確認済み、修正後は FAIL に転じリグレッションを通知）；削除/クリーンアップは実行 id で実行。

### 欠陥 3：webman-scout（elasticsearch クライアント未インストール）→ User/Order/Ticket の書き込みが 500
- 現象：`PUT /api/user/profile`（復元含む）、`POST /api/orders`、`POST /api/tickets` がすべて HTTP 500 `Server internal error` を返す（ログは `ScoutException: Please install the ElasticSearch client`）。
- 根本原因：User/Product/Ticket/Order モデルが `Scout\Searchable` trait を持ち（config/plugin/webman-scout のデフォルト driver=elasticsearch）、`elasticsearch/elasticsearch` クライアントが未インストール → モデル保存時のインデックス同期で例外。
- 影響面：ユーザーのプロフィール変更、注文、チケット提出がすべて使用不可（カート/カート追加は影響なし）。
- 修正提案：elasticsearch クライアントをインストールして利用可能な ES サービスを設定、または検索を有効にしない場合は driver を `database`/`null` に切り替え。
- テスト処理：欠陥プローブでアサート（PASS=欠陥確認済み。修正後は FAIL に転じリグレッションを通知）。

## 重要発見：セキュリティプラグインがローカルテストをブロック
- 現在コードの security プラグイン（erikwang2013/security-php）が `dns_rebinding` 検知を有効化：Host ヘッダーが 127.0.0.1/localhost/内部 IP の場合、直接 403 でブロック。連続 5 回で ip_blacklist が 127.0.0.1 を 15 分封禁（保存先 /tmp/security_storage.json、service/admin 共有）。
- 影響：本機からの API テストは外部ホスト名の Host ヘッダー（本レポートのテストは `Host: api.test.local` / `Host: admin.test.local`）が必須。そうしないと全部 403。
- この挙動はコードの現在状態（18:37 コミット後の新規設定）。以前 14:08 に起動した旧プロセスにはこの設定がなく、旧レポートにはこのブロックが見られない。

## 実行方法
```bash
# 前置条件：service 8787 + admin 8788 稼働中；MySQL/Redis 利用可能
php tests/api/run_api_e2e.php
```
- 冪等性：スクリプトは繰り返し実行可能（実行ごとに新規テストアカウント（SQL 直接挿入）、新シードデータを作成し、終了後にクリーンアップ）。
- 注意：以前のテストでセキュリティ封禁が発火した場合（/tmp/security_storage.json に 127.0.0.1 ban が存在）、そのファイルを削除するか 15 分待つ必要がある。
