## एप्लिकेशन दोष (वर्तमान कोड, पुनः प्रस्तुत)

### दोष 1：encryptable डेटाबेस फ़ील्ड एन्क्रिप्शन कुंजी लंबाई गलत → सभी एन्क्रिप्टेड फ़ील्ड लेखन 500
- घटना：`POST /api/auth/register`、`POST /api/auth/login` (सही पासवर्ड)、`POST /api/auth/refresh`、`POST /api/user/addresses` सभी HTTP 500 `Server internal error` लौटाते हैं (register एन्क्रिप्टेड चैनल में 200 + payload के रूप में लिपटा है, डिक्रिप्ट करने पर भी `Server internal error`)।
- मूल कारण：`.env` में `ENCRYPTION_CIPHER=aes-128-ecb` (16 बाइट कुंजी चाहिए) + `ENCRYPTION_KEY=YKBEUxiX/G8HwVS4S+/UxQ==` (base64 एन्कोडेड 16 बाइट, पर कोड base64_decode नहीं करता, वास्तविक लंबाई 24 अक्षर) → `vendor/erikwang2013/encryptable/src/Encrypter.php:74` पर `MissingEncryptionKeyException: The encryption key must be 16 bytes for cipher [aes-128-ecb]`।
- प्रभाव क्षेत्र：सभी `Encryptable` cast वाले मॉडल लेखन：users (email/phone/password_hash)、refresh_tokens (token_hash/device_fingerprint)、user_addresses (phone/address)、user_kyc、payment_channels、suppliers、host_machines、provider_api। अर्थात：पंजीकरण, लॉगिन token जारी, token रिफ्रेश, पता जोड़ना सभी अनुपलब्ध।
- फिक्स सुझाव：`config/encryptable.php` में `ENCRYPTION_KEY` पर `base64_decode` करें (या .env में सीधे 16 बाइट सादा कुंजी डालें)।
- टेस्ट हैंडलिंग：लॉगिन के बाद token टेस्ट स्क्रिप्ट सीधे `JwtAuth::issueAccessToken` (समान कुंजी) से जारी कर आगे की श्रृंखला चलाती है; पंजीकरण/लॉगिन/रिफ्रेश/पता निर्माण दोष-प्रोब एसर्शन के अनुसार (PASS का मतलब दोष पुष्ट, फिक्स के बाद यह एसर्शन FAIL होकर रिग्रेशन संकेत देगा)।

### दोष 2：admin मॉडल `erik_*` टेबल की ओर इशारा करते हैं (रिपॉजिटरी माइग्रेशन में नहीं) → टेबल गायब होने पर CRUD पूरी तरह टूटा / टेबल मौजूद होने पर service डेटा से अलग
- घटना：`admin/app/model/*.php` सभी `protected $table = 'erik_*'` घोषित करते हैं। टेस्ट के दौरान दो रूप देखे गए：
  1. erik_* टेबलें मौजूद नहीं (वर्तमान DB स्थिति, erik_* टेबलें समवर्ती वातावरण परिवर्तन से हटा दी गईं)：9/12 admin `/select` डेटा एंडपॉइंट `code=42 SQLSTATE[42S02] ... Table 'cloud_platform.erik_orders/erik_products/...' doesn't exist` लौटाते हैं；`/insert` भी 42। केवल user/role/audit_log जो वास्तविक टेबलों की ओर इशारा करते हैं उपलब्ध हैं (user→users、role→wa_roles)。
  2. erik_* टेबलें हाथ से बनाई गईं (टेस्ट के बीच दूसरे agent द्वारा बनाई गईं, थोड़ी देर मौजूद रहीं)：admin `/select`、`/insert`、`/delete` सभी code=0 उपलब्ध, पर लेखन `erik_products` में जाता है, service केवल `products` पढ़ता है → admin द्वारा बनाया उत्पाद शॉपिंग सूची में दिखाई नहीं देता (प्रोब एसर्शन listed=n से पुष्टि, फिक्स के बाद FAIL होकर रिग्रेशन संकेत देगा)।
- परिशिष्ट (अवलोकित विसंगति)：E2E पूर्ण रन के दौरान `POST /app/admin/product/insert` का उत्तर देने वाला id(hashid) वास्तविक डेटाबेस पंक्ति id से अलग था (जैसे उत्तर nE6vQwlYejMd→350964708271980544 बनाम वास्तविक पंक्ति 350963879578173440), उत्तर id से delete बुलाने पर code=0 पर कोई मेल खाती पंक्ति नहीं, चुपचाप खाली डिलीट (दो पूर्ण रन में दोनों बार दोहराया गया)；पृथक प्रोब (लॉगिन के तुरंत बाद insert) में दोहराया नहीं गया, संदेह अनुरोध समय/स्नोफ्लेक ID जनरेशन से संबंधित, गहराई से जाँच नहीं की गई। टेस्ट स्क्रिप्ट अब slug द्वारा वापस वास्तविक पंक्ति id खोजकर डिलीट/क्लीनअप करती है।
- प्रभाव क्षेत्र：admin पैनल और शॉपिंग फ्रंट डेटा श्रृंखला टूट गई (admin द्वारा प्रबंधित डेटा शॉपिंग में अदृश्य, और उल्टा)；insert उत्तर id अविश्वसनीय होने से क्लाइंट डिलीट/अपडेट चुपचाप विफल हो सकते हैं।
- फिक्स सुझाव：admin मॉडल `$table` से `erik_` प्रत्यय हटाकर service वास्तविक टेबलों की ओर एकरूप करें (और माइग्रेशन/सीड जोड़ें)；insert उत्तर id जनरेशन श्रृंखला की जाँच करें।
- टेस्ट हैंडलिंग：सूची दोष-प्रोब एसर्शन के अनुसार (code=0 या SQL 1146 दोनों PASS=दोष पुष्ट, फिक्स के बाद FAIL होकर रिग्रेशन संकेत देगा)；डिलीट/क्लीनअप वास्तविक पंक्ति id से किया गया।

### दोष 3：webman-scout (elasticsearch क्लाइंट स्थापित नहीं) → User/Order/Ticket लेखन 500
- घटना：`PUT /api/user/profile` (पुनर्स्थापना सहित)、`POST /api/orders`、`POST /api/tickets` सभी HTTP 500 `Server internal error` लौटाते हैं (लॉग में `ScoutException: Please install the ElasticSearch client`)।
- मूल कारण：User/Product/Ticket/Order मॉडल में `Scout\Searchable` trait है (config/plugin/webman-scout डिफ़ॉल्ट driver=elasticsearch), पर `elasticsearch/elasticsearch` क्लाइंट स्थापित नहीं → मॉडल सेव करते समय समकालिक इंडेक्सिंग अपवाद फेंकती है।
- प्रभाव क्षेत्र：उपयोगकर्ता प्रोफ़ाइल बदलना, ऑर्डर देना, टिकट सबमिट करना सभी अनुपलब्ध (शॉपिंग कार्ट/जोड़ना प्रभावित नहीं)।
- फिक्स सुझाव：elasticsearch क्लाइंट स्थापित कर उपलब्ध ES सेवा कॉन्फ़िगर करें, या driver को `database`/`null` में बदलें (खोज सक्षम न होने पर)।
- टेस्ट हैंडलिंग：दोष-प्रोब एसर्शन के अनुसार (PASS=दोष पुष्ट; फिक्स के बाद FAIL होकर रिग्रेशन संकेत देगा)।

## महत्वपूर्ण खोज：सुरक्षा प्लगइन स्थानीय टेस्ट को रोकता है

- प्रभाव：इस मशीन से API टेस्ट करते समय बाहरी होस्टनाम Host हेडर साथ भेजना अनिवार्य है (इस रिपोर्ट के टेस्ट `Host: api.test.local` / `Host: admin.test.local` उपयोग करते हैं), अन्यथा सभी 403।
- यह व्यवहार कोड की वर्तमान स्थिति है (18:37 कमिट के बाद नई कॉन्फ़िगरेशन), पहले 14:08 शुरू की गई पुरानी प्रक्रिया में यह कॉन्फ़िगरेशन नहीं था, इसलिए पुरानी रिपोर्ट में यह रुकावट नहीं दिखी।
