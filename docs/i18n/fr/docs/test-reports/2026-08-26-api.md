## Détail des échecs
- `POST /api/auth/register(chiffré)` [auth-flow] status=-1 attendu=0 remarque : code=-1 msg= dans l'enveloppe = Server internal error —— le cast Encryptable du modèle User manque d'une clé de 16 octets (aes-128-ecb), la création d'utilisateur renvoie 500 (défaut applicatif)
- `POST /api/auth/register(texte clair)` [auth-flow] status=500 attendu=200 remarque : HTTP 500 body=Server internal error —— clé Encryptable manquante (défaut applicatif)
- `POST /api/auth/login` [auth-flow] status=200 attendu=200 remarque : code=401 msg=Invalid credentials —— le défaut d'inscription bloque la chaîne de login complète (le captcha est à usage unique, sa réutilisation renvoie 422)

## Remarques sur les limites
- Le paiement Stripe est un service externe : `POST /api/orders/{id}/pay` ne vérifie que le chemin de gestion d'erreur (4xx/5xx), aucun paiement réel ne peut aboutir
- Endpoints `/admin/api/*` du service : un token utilisateur lambda doit renvoyer 401/403 (AdminRole/RBAC) ; le token admin nécessite un compte admin côté service (non configuré dans cet environnement)
- Le problème de clé principale admin (B1) est corrigé et retesté : 8788 démarre normalement, tous les endpoints captcha/dashboard/dict/export/login/CRUD fonctionnent (la copie a été mise à jour avec le fichier de routes complet)
- Panneau admin (copie 8788) : toutes les routes fonctionnent, la chaîne de login (captcha+session+bcrypt) renvoie bien un token ; point d'observation : les endpoints de liste user/order/product/config sont accessibles sans cookie de session (HTTP 200, non authentifié)
- Inscription (les deux chemins service renvoient 500) : le cast Encryptable du modèle User manque d'une clé de 16 octets (aes-128-ecb, MissingEncryptionKeyException) → inscription indisponible, impossible d'obtenir un token utilisateur, l'ensemble des cas d'authentification avec token est sauté ; le login ne peut vérifier que les chemins d'erreur 401/422 car le captcha est à usage unique et aucun utilisateur n'existe
- Endpoints publics : lors de cette passe de re-test, products/{id}, help/{slug}, stripe webhook et domain/* sont tous revenus à la normale (le 500 ModelNotFoundException précédent et le problème de colonnes manquantes de domain_tlds sont corrigés)
- Limitation de débit : par défaut 60 req/60s par IP, le test l'évite avec un intervalle de 1 s, quelques 429 transitoires sont attendus
- WAF (plugin security-php) : le détecteur dns_rebinding classe Host=127.0.0.1 comme adresse interne et le bloque à tort (problème de configuration applicative, catégorie W1-W3) ; ce jeu de tests contourne le blocage en envoyant un Host de domaine via la variable d'environnement `TEST_HOST` (forme de déploiement réelle) ; la mise en liste noire IP automatique (max_attempts=5) est stockée en fichier et se lève automatiquement 15 minutes après le trafic de test
