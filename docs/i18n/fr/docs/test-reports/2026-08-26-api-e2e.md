## Défauts applicatifs (code courant, reproduits)

### Défaut 1 : longueur de clé de chiffrement incorrecte pour les champs encryptable → toutes les écritures de champs chiffrés renvoient 500
- Phénomène : `POST /api/auth/register`, `POST /api/auth/login` (mot de passe correct), `POST /api/auth/refresh`, `POST /api/user/addresses` renvoient tous un HTTP 500 `Server internal error` (register passe par le canal chiffré et ressort en 200 + payload, mais le déchiffrement donne aussi `Server internal error`).
- Cause racine : dans `.env`, `ENCRYPTION_CIPHER=aes-128-ecb` (exige une clé de 16 octets) + `ENCRYPTION_KEY=YKBEUxiX/G8HwVS4S+/UxQ==` (16 octets encodés en base64, mais le code n'appelle pas base64_decode, la longueur réelle est de 24 caractères) → `vendor/erikwang2013/encryptable/src/Encrypter.php:74` lève `MissingEncryptionKeyException: The encryption key must be 16 bytes for cipher [aes-128-ecb]`.
- Périmètre : toutes les écritures des modèles avec cast `Encryptable` : users (email/phone/password_hash), refresh_tokens (token_hash/device_fingerprint), user_addresses (phone/address), user_kyc, payment_channels, suppliers, host_machines, provider_api. Autrement dit : inscription, émission de token au login, rafraîchissement de token et ajout d'adresse sont tous indisponibles.
- Suggestion de correctif : appliquer `base64_decode` à `ENCRYPTION_KEY` dans `config/encryptable.php` (ou placer une clé en clair de 16 octets dans .env).
- Traitement du test : après le login, le token est émis directement par le script via `JwtAuth::issueAccessToken` (même clé) pour débloquer le reste de la chaîne ; inscription/login/refresh/création d'adresse font l'objet d'assertions de sonde de défaut (PASS = défaut confirmé ; une fois corrigé, cette assertion basculera en FAIL pour signaler la régression).

### Défaut 2 : les modèles admin mappent les tables `erik_*` (hors migrations du dépôt) → CRUD entièrement cassé si la table manque / données déconnectées du service si la table existe
- Phénomène : tous les `admin/app/model/*.php` déclarent `protected $table = 'erik_*'`. Deux formes ont été observées pendant le test :
  1. Tables erik_* absentes (état actuel de la DB, les tables erik_* ayant été supprimées par le changement d'environnement concurrent) : 9 des 12 endpoints de données `/select` admin renvoient `code=42 SQLSTATE[42S02] ... Table 'cloud_platform.erik_orders/erik_products/...' doesn't exist` ; `/insert` renvoie aussi 42. Seuls user/role/audit_log, qui mappent des tables réelles, fonctionnent (user→users, role→wa_roles).
  2. Tables erik_* créées manuellement (existence brève après la création par l'autre agent en cours de test) : les `/select`, `/insert`, `/delete` admin renvoient tous code=0, mais les écritures atterrissent dans `erik_products`, alors que le service ne lit que `products` → les produits créés dans admin sont invisibles dans la liste du magasin (confirmé par l'assertion de sonde listed=n ; passera en FAIL après correction pour signaler la régression).
- Note (anomalie observée) : lors des exécutions E2E complètes, l'id (hashid) renvoyé par la réponse de `POST /app/admin/product/insert` diffère de l'id réellement inséré en base (ex. réponse nE6vQwlYejMd→350964708271980544 vs ligne réelle 350963879578173440) ; appeler delete avec l'id de la réponse renvoie code=0 mais sans ligne correspondante, suppression vide silencieuse (reproduit lors des deux exécutions complètes) ; les sondes isolées (insert immédiatement après login) ne reproduisent pas le problème, probablement lié au timing des requêtes / à la génération des IDs Snowflake, non approfondi. Le script de test a été modifié pour réinterroger l'id réel de la ligne par slug pour la suppression/nettoyage.
- Périmètre : la liaison de données entre le panneau admin et la boutique est rompue (les données gérées dans admin sont invisibles en boutique, et inversement) ; un id de réponse d'insert non fiable peut faire échouer silencieusement les suppressions/mises à jour côté client.
- Suggestion de correctif : retirer le préfixe `erik_` de `$table` dans chaque modèle admin pour pointer uniformément vers les tables réelles du service (et compléter migrations/seeds) ; enquêter sur la chaîne de génération de l'id de réponse d'insert.
- Traitement du test : les listes utilisent des assertions de sonde de défaut (code=0 ou SQL 1146 → PASS = défaut confirmé ; passeront en FAIL après correction) ; suppression/nettoyage exécutés avec l'id réel de la ligne.

### Défaut 3 : webman-scout (client Elasticsearch non installé) → écritures User/Order/Ticket en 500
- Phénomène : `PUT /api/user/profile` (y compris restauration), `POST /api/orders`, `POST /api/tickets` renvoient tous un HTTP 500 `Server internal error` (log : `ScoutException: Please install the ElasticSearch client`).
- Cause racine : les modèles User/Product/Ticket/Order portent le trait `Scout\Searchable` (driver par défaut = elasticsearch dans config/plugin/webman-scout), mais le client `elasticsearch/elasticsearch` n'est pas installé → l'indexation synchrone à la sauvegarde du modèle lève une exception.
- Périmètre : modification du profil, passation de commande et dépôt de ticket tous indisponibles (panier/ajout au panier non affectés).
- Suggestion de correctif : installer le client Elasticsearch et configurer un service ES disponible, ou passer le driver à `database`/`null` (si la recherche n'est pas activée).
- Traitement du test : assertions de sonde de défaut (PASS = défaut confirmé ; passeront en FAIL après correction).

## Découverte importante : le plugin de sécurité bloque les tests locaux
- Le plugin security du code courant (erikwang2013/security-php) active la détection `dns_rebinding` : lorsque le header Host est 127.0.0.1/localhost/IP interne, il renvoie un 403 directement, et après 5 occurrences consécutives, ip_blacklist bannit 127.0.0.1 pendant 15 minutes (stockage /tmp/security_storage.json, partagé entre service et admin).
- Impact : pour tester l'API depuis la machine locale, il faut envoyer un header Host avec un nom d'hôte externe (ce rapport utilise `Host: api.test.local` / `Host: admin.test.local`), sinon tout renvoie 403.
- Ce comportement fait partie de l'état actuel du code (nouvelle configuration ajoutée au commit de 18:37) ; l'ancien processus démarré à 14:08 ne l'avait pas, d'où son absence dans les rapports précédents.
