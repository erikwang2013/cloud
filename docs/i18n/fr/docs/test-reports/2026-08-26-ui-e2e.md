## Analyse des problèmes et échecs

### Problème 1 (faux positif, pas un défaut) : `Cannot read properties of undefined (reading 'Account')` en navigation directe
- Phénomène : lors du balayage, la connexion directe à `/app/admin/xxx/index` fait remonter `window.Admin.Account` undefined dans permission.js.
- Cause : `window.Admin` n'est injecté que dans le cadre principal index.html ; il manque quand on se connecte directement à une sous-page (sans cadre principal).
- Conclusion : le chemin d'utilisation réel (clic sur la barre latérale pour entrer dans l'iframe) ne présente pas cette erreur, ce n'est pas un défaut.

### Problème 2 (vrai petit défaut) : `<img src="null">` déclenche un 404 quand l'avatar est vide
- Phénomène : au chargement de la liste user, requête `/app/admin/user/null` → erreur console 404.
- Cause racine : `admin/app/view/user/index.html:273` (identique dans admin/index.html) :
  `'<img src="'+encodeURI(d['avatar'])+'" ...'` — quand la ligne avatar est NULL, `encodeURI(null)` → chaîne `"null"`, que le navigateur résout en chemin relatif `/app/admin/user/null`.
- Impact : seules les lignes à avatar vide affichent une image cassée + 1 log 404 console, aucun impact fonctionnel.
- Suggestion : `encodeURI(d['avatar'] ?? '')` ou ne pas rendre l'img sur valeur vide.

### Problème 3 (différence d'environnement, pas un défaut) : 36 modèles pointent vers des tables `erik_*` absentes de la base
- Phénomène : les tables réelles de la base sont `orders/products/...`, alors que dans `admin/app/model/` 36 modèles ont `$table = 'erik_xxx'`, ce qui fait que ces listes n'affichent aucune donnée (la page elle-même se rend correctement en 200).
- Explication : la chaîne de rendu des données de ces pages a été validée via un `CREATE TABLE erik_* LIKE table_de_base` temporaire + insertion de lignes de test e2e_, puis tout a été supprimé après validation (0 table `erik_%` actuellement). C'est un problème d'environnement lié à une incohérence de nommage, à uniformiser plus tard.

## Comment relancer

```bash
# 1. Démarrer/confirmer l'instance de test (code synchronisé avec le repo, écoute sur 8788)
# 2. Lancer le script principal (connexion → balayage 51 pages → navigation iframe → fenêtre de détail → déconnexion)
node /tmp/ui-e2e2/run-e2e.js
# 3. Navigation de menus + fenêtre de détail spécifique (problème de capture frame corrigé)
node /tmp/ui-e2e2/final-nav-test.js
```

Points essentiels :
- La connexion a une limitation de fréquence : 5 requêtes/minute sur l'interface de connexion, 60/min pour le balayage complet des pages (RateLimitMiddleware, fenêtre glissante Redis). Le script attend 61 s et réessaie sur 429 (4 fois max) ; prévoir ≥ 65 s d'intervalle entre deux exécutions.
- Le code de vérification est lu depuis `runtime/sessions/session_<PHPSID>`, php CLI doit être exécutable.
- Les résultats sortent dans `/tmp/ui-e2e2/results.json`, les captures dans `docs/test-reports/screenshots/2026-08-26-e2e/`.
- Pour valider le rendu des données de liste : créer d'abord des copies de tables `erik_*` d'après `admin/app/model/` et insérer des lignes de test (`/tmp/ui-e2e2/create-erik-copies.sql.sh` + `seed.sh`), puis nettoyer avec `drop-erik-copies.sql.sh` + `rollback-seed.sh` après exécution.
