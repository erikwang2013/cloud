# Relatório de Testes E2E da API CloudPlatform (2026-08-26)

## Ambiente
- service: http://127.0.0.1:8787 (`php start.php start -d`, reiniciado antes desta rodada para carregar o código atual após o commit de renomeação das 18:37)
- admin: http://127.0.0.1:8788 (cópia /tmp/cp-admin-ui, código idêntico ao admin do repositório, iniciado em sincronia às 13:56)
- PHP 8.3.7 / webman 5.2.2 / MySQL 3306 (cloud_platform, tabelas de negócio vazias) / Redis 6379
- Contas de teste: `apitest-e2e-{ts}@test.local` (usuário do service, inserido via SQL direto — o endpoint de registro tem defeito de aplicação e não cria contas, ver resumo de defeitos); `apitestadmin` (painel admin, com papel SuperAdmin concedido temporariamente durante o teste e removido após)
- Dados de teste: 1 categoria + 1 produto published (seed via SQL, excluído após o teste); chamados/endereços/notificações são dados dentro da conta de teste
- Script: `php tests/api/run_api_e2e.php`
- Mudança de ambiente: durante o teste, outro agent criou manualmente tabelas erik_* (não são migrações do repositório) e depois as removeu; por isso as duas formas do defeito 2 (tabela ausente 1146 / tabela existente mas dados desconectados) foram observadas e registradas

## Defeitos da Aplicação (código atual, reproduzidos)

### Defeito 1: comprimento errado da chave de criptografia de campos do banco → todas as escritas em campos criptografados retornam 500
- Sintoma: `POST /api/auth/register`, `POST /api/auth/login` (senha correta), `POST /api/auth/refresh`, `POST /api/user/addresses` retornam HTTP 500 `Server internal error` (register embrulhado pelo canal criptografado retorna 200 + payload, que após decriptação também é `Server internal error`).
- Causa raiz: `ENCRYPTION_CIPHER=aes-128-ecb` no `.env` (exige chave de 16 bytes) + `ENCRYPTION_KEY=YKBEUxiX/G8HwVS4S+/UxQ==` (16 bytes codificados em base64, mas o código usa sem base64_decode, comprimento real de 24 caracteres) → `vendor/erikwang2013/encryptable/src/Encrypter.php:74` lança `MissingEncryptionKeyException: The encryption key must be 16 bytes for cipher [aes-128-ecb]`.
- Impacto: toda escrita em modelos com cast `Encryptable`: users (email/phone/password_hash), refresh_tokens (token_hash/device_fingerprint), user_addresses (phone/address), user_kyc, payment_channels, suppliers, host_machines, provider_api. Ou seja: registro, emissão de token no login, refresh de token e criação de endereço ficam todos indisponíveis.
- Sugestão de correção: fazer `base64_decode` de `ENCRYPTION_KEY` em `config/encryptable.php` (ou colocar a chave de 16 bytes em texto puro no .env).
- Tratamento no teste: o token pós-login é emitido pelo próprio script de teste via `JwtAuth::issueAccessToken` (mesma chave) para destravar as cadeias seguintes; registro/login/refresh/criação de endereço são asseridos como sondas de defeito (PASS significa defeito confirmado; após a correção, essa asserção passa a FAIL indicando regressão).

### Defeito 2: modelos do admin mapeiam tabelas `erik_*` (fora das migrações do repositório) → CRUD totalmente quebrado com tabela ausente / dados desconectados do service com tabela existente
- Sintoma: todos os `admin/app/model/*.php` declaram `protected $table = 'erik_*'`. Durante o teste, duas formas foram observadas:
  1. Tabelas erik_* inexistentes (estado atual do banco; as tabelas erik_* foram removidas pela mudança concorrente de ambiente): 9/12 endpoints de dados `/select` do admin retornam `code=42 SQLSTATE[42S02] ... Table 'cloud_platform.erik_orders/erik_products/...' doesn't exist`; `/insert` também retorna 42. Apenas user/role/audit_log, que mapeiam tabelas reais, funcionam (user→users, role→wa_roles).
  2. Tabelas erik_* criadas manualmente (existiram brevemente quando outro agent criou as tabelas no meio do teste): `/select`, `/insert`, `/delete` do admin todos com code=0, mas a escrita cai em `erik_products` enquanto o service lê apenas `products` → produto criado no admin não aparece na lista da loja (sonda assere listed=n confirma; após correção, vira FAIL indicando regressão).
- Nota (anomalia observada): na execução completa do E2E, o id (hashid) retornado por `POST /app/admin/product/insert` não corresponde ao id da linha realmente gravada (ex.: resposta nE6vQwlYejMd→350964708271980544 vs linha real 350963879578173440); usar o id da resposta em delete retorna code=0 mas sem linha correspondente, exclusão vazia silenciosa (reproduzido nas duas execuções completas); a sonda isolada (insert logo após login) não reproduziu, aparentemente relacionado ao timing das requisições/geração de IDs snowflake, não aprofundado. O script de teste passou a consultar o id real da linha por slug para exclusão/limpeza.
- Impacto: a cadeia de dados entre painel admin e vitrine da loja está rompida (dados administrados no admin não aparecem na loja, e vice-versa); o id não confiável na resposta de insert faz exclusões/atualizações do cliente falharem silenciosamente.
- Sugestão de correção: remover o prefixo `erik_` do `$table` dos modelos do admin, apontando para as tabelas reais do service (e completar migrações/seeds); investigar a cadeia de geração do id na resposta de insert.
- Tratamento no teste: listas asseridas como sondas de defeito (code=0 ou SQL 1146 ambos PASS = defeito confirmado; após correção vira FAIL); exclusão/limpeza usa o id real da linha.

### Defeito 3: webman-scout (cliente elasticsearch não instalado) → escritas em User/Order/Ticket retornam 500
- Sintoma: `PUT /api/user/profile` (incluindo restauração), `POST /api/orders`, `POST /api/tickets` retornam HTTP 500 `Server internal error` (log: `ScoutException: Please install the ElasticSearch client`).
- Causa raiz: os modelos User/Product/Ticket/Order têm o trait `Scout\Searchable` (config/plugin/webman-scout com driver padrão=elasticsearch), mas o cliente `elasticsearch/elasticsearch` não está instalado → a indexação síncrona no salvamento do modelo lança exceção.
- Impacto: alterar perfil, fazer pedido e abrir chamado ficam todos indisponíveis (carrinho/adicionar ao carrinho não são afetados).
- Sugestão de correção: instalar o cliente elasticsearch e configurar um serviço ES utilizável, ou trocar o driver para `database`/`null` (quando a busca não estiver ativada).
- Tratamento no teste: asserido como sonda de defeito (PASS = defeito confirmado; após correção vira FAIL).

## Descoberta importante: plugin de segurança bloqueando testes locais
- O plugin de segurança do código atual (erikwang2013/security-php) ativa a detecção `dns_rebinding`: com Host 127.0.0.1/localhost/IP interno, intercepta com 403 na hora; após 5 vezes consecutivas, a ip_blacklist bane 127.0.0.1 por 15 minutos (armazenamento em /tmp/security_storage.json, compartilhado entre service e admin).
- Impacto: para testar a API a partir da própria máquina é obrigatório enviar Host com nome de domínio externo (este relatório usou `Host: api.test.local` / `Host: admin.test.local`), senão tudo retorna 403.
- Esse comportamento é o estado atual do código (configuração nova adicionada após o commit das 18:37); o processo antigo iniciado às 14:08 não tinha essa configuração, por isso os relatórios antigos não mostram essa interceptação.

## Como Executar
```bash
# Pré-requisito: service 8787 + admin 8788 rodando; MySQL/Redis disponíveis
php tests/api/run_api_e2e.php
```
- Idempotência: o script pode ser executado repetidamente (cria nova conta de teste a cada execução (inserção direta via SQL), novos dados de seed, e limpa tudo ao final).
- Atenção: se uma execução anterior tiver disparado o bloqueio de segurança (/tmp/security_storage.json com ban de 127.0.0.1), exclua o arquivo ou aguarde 15 minutos.
