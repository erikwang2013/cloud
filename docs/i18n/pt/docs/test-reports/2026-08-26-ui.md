## 3. Problemas Bloqueantes (em ordem de dependência)

### B1. Formato de ENCRYPTION_MASTER_KEY incompatível com o código → worker do admin morre na inicialização
- **Sintoma**: após `php start.php start`, os 4 workers todos saem com exceção (porta fica ocupada mas requisições nunca respondem, conexões acumulando no accept backlog); log:
  `InvalidArgumentException: Master key must be exactly 32 bytes. in vendor/erikwang2013/encryption/src/EncryptionManagerFactory.php:29`
- **Causa raiz**: `ENCRYPTION_MASTER_KEY=y1Odnbg50NHEvvLHGb8aexKqy8AQ7izm0x+yoEgrYCU=` no `admin/.env` é **base64 de 44 bytes**; `EncryptionManagerFactory::fromMasterKey()` exige **32 bytes brutos** (o comentário em `admin/config/encryption.php:30` também diz "64 hex characters"). Porém `.env.example:64` marca como base64 — contrato entre configuração e código contraditório.
- **Complemento**: `support/bootstrap.php:47` usa `Dotenv::createUnsafeMutable()->load()`, e a **sobreposição de env no nível do processo é substituída pelos valores do .env**; não é possível contornar com argumento de inicialização (testado duas vezes, ambas falharam).
- O resultado do base64 decode dessa key é exatamente 32 bytes (hex `cb539d9d…6025`), ou seja, o formato correto = o valor após o base64 decode.

### B2. `config/database.php` ausente → camada de banco inexistente
- **Sintoma**: `/account/login` → 500 `BusinessException: 请重启webman` (`app/controller/AccountController.php:263` `checkDatabaseAvailable()`, lança quando `!config('database')`).
- **Causa raiz**: o arquivo é gerado pelo assistente de instalação e está no gitignore; nunca existiu no repositório (`git ls-files` sem registro). `config/thinkorm.php` também ausente.

### B3. `install.sql` ausente → assistente de instalação não executa
- **Sintoma**: o assistente `step1` (`InstallController.php:105`) verifica `base_path().'/install.sql'`; ausente → retorna "arquivo SQL do banco não existe". O arquivo não existe no repositório.
- Impacto: o único caminho oficial para corrigir B2 (assistente de UI) também não funciona.

### B4. Todos os recursos estáticos das views usam prefixo `/app/admin/`, sem mapeamento algum → UI inteira sem estilo, JS 404
- **Sintoma** (medido na página de login/página de instalação/framework principal): `/app/admin/component/pear/css/pear.css`, `/app/admin/admin/css/reset.css`, `/app/admin/component/layui/layui.js` etc. todos 404; `ReferenceError: layui is not defined`; formulários não enviam.
- **Causa raiz**: os arquivos estáticos estão realmente em `public/admin/`, `public/component/` (webman serve via `/admin/...`, 200 medido); mas `app/view/account/login.html`, `app/view/index/install.html`, `app/view/index/index.html` etc. referenciam todos `/app/admin/...`. `config/route.php` tem apenas 4 rotas explícitas `/app/admin/` (captcha/dict/dashboard-data/table-export); `config/static.php` não tem mapeamento de prefixo; `docker/nginx.conf` e `docker/nginx-admin.conf` também não têm `location /app/admin`. O frontend e o backend têm convenções de URL totalmente inconsistentes (POST de formulário `/app/admin/account/login` → 404; o endpoint real deveria estar na raiz `/account/login`).

### B5. Alvo do redirecionamento não logado errado → páginas de negócio viram página 404 do Chrome
- **Sintoma** (medido em /user/index, /order/index, /product/index, /supplier/index, /config/index, /role/index, /admin/index, /ticket/index, /index/dashboard, /dashboard/index): retorna 200, mas a página é redirecionada via JS para `http://127.0.0.1:8788/app/admin` → essa URL dá 404 → renderiza a página "não encontrado" do Chrome.
- **Causa raiz**: `app/middleware/AccessControl.php:45` não logado retorna `admin_error_401_script()` (`app/functions.php:93`), cujo conteúdo é `<script>top.location.href = '/app/admin';</script>` — o endereço da página de login está fixado em `/app/admin`, o mesmo erro de convenção de caminho do B4.
- Acessório: `/payment_channel/index`, `/coupon/index`, `/domain_tld/index`, `/dns_zone/index`, `/invoice/index`, `/report/index` falham direto com `ERR_HTTP_RESPONSE_CODE_FAILURE` (falha já na camada de controlador/rota, não chega ao redirecionamento).

### B6. 500 na raiz: dados de `system_config` ausentes
- **Sintoma**: após completar a configuração do B2 manualmente, `GET /` (renderização da página de login via `IndexController::index`) → 500 `ErrorException: json_decode(): Passing null to parameter #1 … in app/controller/IndexController.php:49`.
- **Causa raiz**: `Option::where('name','system_config')->value('value')` retorna null (não existe a linha no banco — este banco não foi criado pelo assistente de instalação); `json_decode(null)` no PHP 8.3 dispara deprecation e lança erro. Ou seja, a página de login quebra direto quando os dados não foram inicializados pelo assistente.

## 5. Resumo dos Defeitos de UI Encontrados

### Primeira rodada (ambiente original, bloqueantes)

1. **B1 (bloqueante)** chave mestra do .env em base64 vs exigência de 32 bytes do código → serviço nem inicia. Reprodução: `cd admin && php start.php start -d`.
2. **B2/B3 (bloqueantes)** artefatos de instalação ausentes (config/database.php, install.sql), e o assistente em si não executa → aplicação não inicializa.
3. **B4 (bloqueante)** caminhos de recursos das views `/app/admin/...` inconsistentes com a localização real dos arquivos estáticos/prefixo de rota → sem estilo, sem JS, formulários inutilizáveis.
4. **B5 (bloqueante)** redirecionamento 401 não logado fixado em `/app/admin` → todas as páginas de negócio caem em link morto.
5. **B6** a renderização da página de login não tem fallback para a linha `system_config` ausente; `json_decode(null)` dá 500 direto (deprecation do PHP 8.3 elevada a exceção).

### Segunda rodada (medido logado, problemas sistêmicos)

6. **W1. WAF mata URLs de negócio legítimas**: `admin/app/middleware/WafMiddleware.php:75` varre o path da URL com regex de SQLi/XSS (`config/security.php`: `\b(union|select|insert|update|delete|drop|...)\b`, `\balert\b` etc.):
   - `/alert/index` bate na regra XSS por conter "alert" na URL → **403**;
   - todos os endpoints de dados CRUD (`/user/select`, `/user/insert`, `/user/update`, `/user/delete`, `/order/select`…) batem em regras SQLi como `\bselect\b` → **403**.
   - Impacto: **o carregamento de dados de todas as páginas de lista e todas as operações de criar/editar/excluir ficam completamente indisponíveis no navegador** (as requisições `SELECT_API` do frontend ficam todas em 403).
7. **W2. convenção de URL com sublinhado não vale + links de menu todos mortos**: a rota automática do webman não suporta sublinhado no nome do controlador — `/order_item/index` 404, `/orderitem/index` 200 (as 47 páginas só são alcançáveis concatenando a URL em camelCase). Mas todos os hrefs de `config/menu.php` e `config/business_menu.php` são `/app/admin/<snake_case>/index` (ex.: `/app/admin/payment_channel/index`) → **cada item da navegação lateral é um link morto (404 ou 403)**.
8. **W3. constante JS SELECT_API das tabelas não definida**: as constantes `SELECT_API`/`INSERT_API` referenciadas pelo JS das páginas (via `/app/admin/...` 404, resíduo do B4) não são injetadas → as tabelas das páginas de lista renderizam sem dados, sem paginação/busca.
9. **W4. 11-15 erros de console de 404 de recursos estáticos por página**: impacto contínuo do B4 — as 47 páginas 200 ficam todas sem estilo, com `layui is not defined`, formulários e modais inutilizáveis.

**Resumo**: o esqueleto das páginas renderiza (47/51), mas a navegação lateral (W2), o carregamento de dados das tabelas (W3+W1) e todas as escritas CRUD (W1) ficam indisponíveis no navegador — o painel é praticamente inoperável.

## 6. Páginas Não Testadas e Motivos

- **Escritas CRUD (envio de formulários de criar/editar/excluir)**: todos os endpoints de dados são interceptados pelo WAF (W1) + o JS dos formulários está indisponível (B4/W3); nenhuma escrita pode ser concluída via UI. Se W1 e B4 forem corrigidos, é possível complementar os testes pelos endpoints `insert/update/delete`.
- **Páginas pós-login**: todas medidas na segunda rodada (47/51 renderizadas, ver §4.2); não cobertos apenas os saltos de menu (links mortos W2) e o carregamento de dados das tabelas (W1/W3).
- **apps/ (clientes Flutter/HarmonyOS)**: exigem dispositivo real/emulador, fora do escopo desta rodada (conforme convenção da tarefa, foco em Web).
- **Páginas da API de negócio do service**: sem UI Web (8787 `/` e `/install.php` ambos 404, API pura); testes no nível de interface são cobertos pela tarefa #13.
